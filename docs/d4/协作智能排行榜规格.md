## 0. 摘要

1. **定位**。协作智能排行榜是 D4 的科研基础设施与平台的一等产物，职责是把"某协同算法在声明条件下优于另一算法"沉淀为可复核的证据，而不是产出一个标量名次（AWR-06 §8.1）。本文在 AWR-06 §8 的方法学之上，补齐产品与治理层：赛道如何开设与命名、榜单分几层、每页展示什么、Δ 族如何防误读地呈现、赛季如何运转、提交与算力如何配给、留出集与种子如何轮换、每个分数背后的证据如何串成可验证的链、结果如何复核与申诉、版本与归档如何管理，以及 D3 `board.v1` 如何冻结并与 `board.v2` 并存。
2. **赛道矩阵**。赛道由四元组 `(execution_topology, observation_profile, budget_profile, network_profile)` 决定（ADR-D4-20）；本文增补一条绑定规则：同一 Board Version 中每个赛道恰好绑定一个物理档与一个时钟档，使物理档成为赛道的冻结属性而不是混排维度（R-LB-03，FB-01）。方法族（经典规划与优化、MARL、LLM Agent、混合）只是标签与筛选维度，不决定赛道；本文给出"方法族 × 拓扑 × 通信档 × 物理档"的开设矩阵，标明每一格在各阶段是主榜、对照榜、参考列、研究赛道、审计榜还是不开设（§3.4）。
3. **榜单层次**。四层：平台总览（含"总榜"矩阵）→ Suite 榜 → 赛道榜（同一赛道、同一场景集，即 M32 的分析组）→ 条目卡；另设协作画像与运行档案两类跨层视图。总榜只并列展示各 Suite 的名次区间、并列组与分层，不计算、不展示任何跨 Suite 的合成分，也不提供跨 Suite 的排序键（ADR-D4-21 的产品化落实，R-LB-12）。
4. **展示**。前端严格遵循项目设计体系：组件只用 shadcn/ui（`web:ui/components/ui/`），图表与表格只用 lieflat（`web:ui/lf/`），图标只用 morphicons（`web:ui/icons/Icon.tsx`），动效只用 transitions.dev 令牌（`web:styles/motion/tokens.css`），色彩为科技灰、黑、白与单一强调红（`--lf-hero`），不使用 emoji；文案为企业级与工业级行文。D4 榜单使用新路由族 `/lab/leaderboard/*`，D3 的 `/lab/board` 原样保留（§5）。
5. **Δ 族展示**。界面不使用"协作增益"作为任何单一量的名称；Δ 族以"协作诊断"面板呈现，每个量给出固定中英文标签、因果解释范围说明、`n/a` 原因码与有效性条件；Δ 列不出现在缺省榜单表格中，在诊断视图中可排序但排序不产生名次（§6）。
6. **赛季**。赛季为平台级序列，绑定内核主版本与评分主版本；缺省时长 26 周，与留出集"每半年部分轮换、未轮换子集至多连续用于 2 个赛季"对齐（本文设定，FB-14）。预赛季在第 17 周末开启、使用独立的预赛季留出集、成绩不迁入正式赛季；第一赛季在 P1 门（第 21 周末）开启，`kernel_version` 冻结为 1.0.0（ADR-D4-34）。为与 AWR-06 路线图（WP-D4-42、AC-D4-42 在第 31 周）同时成立，第一赛季为 10 周的短赛季，第 31 周末 `closed` 时其留出集全部子集整体退役公开；第二赛季起恢复 26 周与部分轮换（§7.6，FB-23）。每个赛季的结算窗口固定为 28 天，`closed` 有硬上界，逾期未结的申诉以归档勘误处理，不阻止 `closed`（§7.7）。
7. **配额与算力**。`validation` 每团队每 Suite 滚动 7 天 3 次、`holdout` 每团队每 Suite 滚动 28 天 1 次；同时活跃提交每团队不超过 3 个（沿用 `py:bench/submissions.py` `ACTIVE_PER_TEAM = 3`）；配额在受理时于锁内预留、进入 EVALUATING 时转为消耗，消除并发超配；`holdout` 提交在受理时即强制入榜（`visibility = board`，不可改），全部 `holdout` 提交的元数据公开；扫描与冒烟失败不消耗评测配额但另设预检上限；基础设施故障退还配额。评测算力按"每场景集"口径重算：每团队每 Suite 每周满额约 37 vCPU 小时，P0–P1 提交评测池约可容纳 7 个满额团队；P2 期间与论文实验共用 D4 份额，设联合预算与削减顺序（§8.5）。
8. **留出集与种子**。在 AWR-06 §8.7 的加盐承诺与逐 Episode `seed_tag` 绑定之上，本文规定按"轮换子集"分别加盐与承诺（使部分退役公开不暴露未退役子集），为 R-1 新种子复跑设置单独承诺的保留种子池，承诺与 `seed_tag` 的字节编码以 M31 §7.7.4 与 ENC-01、ENC-05 为准，并给出 Ladder 式反馈在 `validation` 与 `holdout` 上的分工（§9，FB-03 至 FB-05）。
9. **证据链**。从团队登记、提交签名、镜像摘要与 SBOM，到逐 Episode 的运行清单、trace 摘要、资源账本、评测结果、`rows.jsonl` 行、治理事件流、`board.json`、Board Version 冻结记录与赛季末公开包，共 17 个证据项 E-01 至 E-17，逐项规定生成者、绑定方式、存放、保留期与验证者；`board.json` 由 `rows.jsonl`、榜单配置与治理事件流三者逐字节重算；运营操作写入哈希链审计日志，每日锚定摘要；泄露审计的自动检出先分诊、后处置（§10）。
10. **复核与申诉**。条目的统计有效性（`status`）与复核状态（`verification ∈ {provisional, verified, under_review, revoked}`）分为两个正交字段；`verified` 沿用 AWR-06 §8.10 的 R-1 至 R-4，R-1 与 R-2b 的判据采用 M32 F-39 的预测区间；复核在赛季中滚动进行；申诉分 5 类、设受理与裁决时限、二审与回避规则；处置分 SN-0 至 SN-3 四级，裁决以公告发布；参赛团队成员不得对本团队条目担任评测、复核或双人批准角色（§11）。
11. **版本化与归档**。Board Version 冻结项与变更处置沿用 AWR-06 §8.9 并采纳 M31 §7.9 的版本位细化；Board Version 标识兼容 `py:bench/boardstore.py` 的版本名正则；赛季结束后形成只读归档包，保留只读复现支持一个赛季（ADR-D4-35，§12）。
12. **契约与迁移**。给出 `drone4d.suite.board.v2` 与 `drone4d.suite.submission.v2` 的字段规格（在 AWR-06 §4.7 与 M32 §7.3 之上增补治理字段，均标"待 CT 定稿"）；`board.v1` 冻结只读、继续承载 D3 榜单，`board.v2` 只用于新榜；`lane` 作为 `scenario_set` 的兼容别名保留一个主版本；D-1、D-2、D-6 以脚注与影子重算报告披露（§13、§14）。
13. **规模**。需求 97 条（R-LB-01 至 R-LB-97）、验收 36 条（AC-LB-01 至 AC-LB-36）、风险 12 条、待决 11 条、对 AWR-06 的反馈 30 条（FB-01 至 FB-30）、对并行文档的反馈 9 条（FX-01 至 FX-09）、评审处理记录 20 条。

## 3. 赛道矩阵

### 3.1 赛道定义与绑定属性

赛道由四元组决定（ADR-D4-20）：

| 字段 | 取值 | 说明 |
|---|---|---|
| `execution_topology` | `decentralized`、`centralized` | 分布式赛道要求每 Agent 独立进程或沙箱、`entry.topology = per_agent`（A-03）；集中式只作合法信息的集中式参考列 |
| `observation_profile` | `L1`、`L2-shared`、`L2-own`；`L0`/`T0` 仅用于非排名研究 | 沿用 D3 观测档名 |
| `budget_profile` | `B1`、`B2`、`B-LLM` | 资源上限见 AWR-06 §8.3 预算档表 |
| `network_profile` | `abstract-radio@1`（`default` 参数集）、`ideal@1`、`ns3@1`；`abstract-disk@1` 不成榜 | 不同网络档、不同参数集不混排 |

在四元组之外，本文规定每个赛道在一个 Board Version 内另有以下绑定属性。绑定属性进入赛道定义的摘要 `track_digest`，并随 Board Version 冻结：

| 绑定属性 | 规则 | 理由 |
|---|---|---|
| `physics` | 恰好一个物理档，取自 Suite 清单 `ranked_physics[]`；P0、P1 主赛道为 `planar@1`，P1 门按 Q-D4-12 裁决是否切换为 `kinematic`；切换即新赛季（内核语义变化） | 四元组不含物理档，若 Suite 声明多个合格物理档，不加绑定会导致混排（FB-01） |
| `clock_profile` | 排名运行恒为 `d4_std` | AWR-06 §8.3 网络字段说明 |
| `timing` | `modeled`（缺省）或 `measured`（Timing-Measured 研究赛道） | ADR-D4-20 |
| `network_params_digest` | 网络档参数集的摘要与标签（`synthetic-stress` 或 `calibrated`） | u-ns2 L11；AC-D4-21 |
| `determinism_required` | 主榜、对照榜、参考列为 `1b`；B-LLM 为 `3`；Timing-Measured 为 `none` | AWR-06 §5.6、§8.3 |
| `role` | `main`、`control`、`reference`、`research`、`audit` | §2 |
| `control_of` | 对照榜指向其主榜赛道 id | 对照榜成绩由主榜提交联评生成（§3.6） |

### 3.2 赛道标识语法

AWR-06 的赛道 id（如 `dc-l1-b1-radio`、`tm-l1-b1-radio`、`dc-l2-b2-radio`）在首段混用了拓扑与计时模式，且 `l2` 未区分 `L2-shared` 与 `L2-own`（FB-02）。本文在不改变既有 id 的前提下规定解析语法，新赛道一律按此语法命名：

```
track_id   = topo "-" obs "-" budget "-" net
topo       = "dc" | "cr" | "tm"            ; tm = decentralized + timing=measured（保留 AWR-06 既有用法）
obs        = "l1" | "l2s" | "l2o" | "l2"   ; l2 为 AWR-06 既有 id 的保留写法，含义须在赛道定义中以 observation_profile 显式给出
budget     = "b1" | "b2" | "bllm"
net        = "radio" | "ideal" | "ns3"
```

赛道 id 只作标识，语义以赛道定义中的结构化字段为准；解析器遇到 `l2` 时以结构化字段为权威。

### 3.3 方法族标签

| 标签 | 含义 | 典型方法（来自 AWR-06 §7.6 的算法族覆盖） | 提交时的附加声明 |
|---|---|---|---|
| `classical` | 经典规划、优化与市场机制 | 拍卖、CBBA、匈牙利、滚动 MILP、共识滤波 | 求解器与其许可 |
| `marl` | 多智能体强化学习 | MAPPO、QMIX 类方法 | 训练种子数、训练产物数与摘要（P1 起"训练稳健性"列要求 ≥ 3 个独立训练产物） |
| `llm` | LLM Agent | LLM 规划、LLM 加拍卖 | 模型 id、制品哈希、推理服务版本、采样参数（B-LLM 统计协议） |
| `learned-estimator` | 学习型估计或感知组件 | GNN 融合、学习型 Belief | 训练数据来源 |
| `hybrid` | 上述任意组合 | GNN + MPC、LLM + 拍卖 | 各组成部分的声明并集 |

一个提交可带多个标签（`declared.method_family_tags[]`）；标签由提交者声明，运营方在复核中可要求修正（A-12）。标签只用于筛选、分组展示与协作画像，不决定赛道、不产生独立名次。

## 4. 榜单层次

### 4.1 层次模型

```
平台总览（PG-1）
 ├─ 总榜矩阵：算法标识 × Suite（各 Suite 主榜的名次区间、并列组、分层；无合成）
 └─ Suite 榜（PG-2），每个 Suite 一页
      └─ 赛道榜：分析组 (board_version, track, scenario_set)
           ├─ 视图 1：名次（主排序键 U）
           ├─ 视图 2：资源–效用非支配分层
           ├─ 视图 3：协作诊断（Δ 族，P0 起 Δ_ind、Δ_cut、R_central、G；P1 起 Δ_perm）
           ├─ 视图 4：稳健性（X1，P1 起）
           └─ 条目卡（PG-3）
跨层视图：协作画像（PG-4，按算法标识）、运行档案（公开划分上的 trace 与运行清单）
```

### 4.2 Suite 榜

| 项 | 规定 |
|---|---|
| 页面单元 | 一个 Suite 一页；页内以赛道、场景集、Board Version 三级选择进入分析组 |
| 缺省分析组 | 当前赛季当前 Board Version 的主榜赛道与该 Suite 的首个主场景集 |
| 排序 | 候选条目按 `U` 点估计降序，名次为竞争名次；并列组按"与组首比较"（M32） |
| 区块顺序 | 候选条目（`status = valid`）→ 不完整条目（`incomplete`，不占名次）→ 参考行（`π_ind`、`π_central`、`π_random`，不占名次） |
| 页首信息 | Suite id 与版本、`suite_digest` 前 12 位、赛季与状态、Board Version、赛道绑定属性、`determinism_level`、网络参数标签、`stats` 摘要（估计目标、`n_boot`、ε、`ε_eq`）、条目数、最近一次 `rows.jsonl` 追加时间（UTC） |
| 固定声明 | "名次与区间未经选择校正"；网络参数为 `synthetic-stress` 时显示"网络参数未经实测校准，结论不外推至真实无线环境" |

### 4.3 总榜

总榜回答"某算法在哪些 Suite 上处于什么位置"，不回答"哪个算法总体最好"。

| 项 | 规定 |
|---|---|
| 行 | 算法标识 `algorithm{name, version}` 与团队；同一算法在多个 Suite 的代表条目归入同一行 |
| 列 | 每个 Suite 一组列：主榜名次（含"=" 并列标记）、名次区间、支配层、复核状态；未参与的 Suite 显示"未参与" |
| 缺省排序 | 按算法名称的字典序；可按任一单个 Suite 列排序，排序结果等同于该 Suite 主榜名次，表头注明"按 <Suite> 主榜名次排序" |
| 禁止项 | 不显示 `S_task`、平均名次、名次之和、加权分或任何跨 Suite 合成量；不提供"综合排序"控件 |
| `S_task` 的位置 | 只出现在条目卡与协作画像的摘要区，标注"任务族等权摘要，非排序键"（AWR-06 §8.4） |
| 合成的启用 | 仅当某评分版本经 `drone4d.suite.score.v2` 显式声明 `weights` 与 `composite_scope` 并发布为新 Board Version 时，在该 Board Version 的独立页签显示合成结果，页签标题注明权重来源；缺省不存在该页签 |

### 4.4 研究赛道与负面结果

| 项 | 规定 |
|---|---|
| 接收内容 | 研究赛道条目（Timing-Measured、`ns3@1`）、协作失效诊断报告、负结果报告（u-ns2 L20） |
| 负结果报告的形式 | 提交者提交以平台运行档案为证据的报告（实验规格、Board Version、条目引用、结论与证据），经运营方形式审查后发布在公告页的"研究报告"栏，不产生名次 |
| 展示 | 研究赛道条目卡显示"研究赛道，不排名"；负结果报告与被涉及的条目卡互相链接 |

## 6. Δ 族展示

### 6.1 标签与解释

design-r2 的 `Δ_coop` 已由 Δ 族取代（ADR-D4-22）。界面不使用"协作增益"作为任何单一量的名称；Δ 族面板统一标题为"协作诊断"。各量的固定标签如下（键名为建议，文案以 i18n 核对为准）：

| 量 | 中文标签 | 英文标签 | 因果解释范围（悬浮说明的固定文本要点） | 符号含义 |
|---|---|---|---|---|
| `Δ_ind` | 相对独立参考的净收益 | Net gain over independent reference | 系统级净收益；不是机制因果；未同时给出 `Δ_perm` 时不得与"协作"并列 | 正值表示优于零通信的独立团队 |
| `Δ_cut` | 通信依赖度 | Channel reliance | 阻断全部投递后的效用损失；对脆弱策略会虚高；不得称为协作增益 | 正值表示依赖显式通信 |
| `Δ_perm`（`perm_struct` 主口径，`perm_full` 并报） | 消息内容敏感度 | Message content sensitivity | 干预性敏感度；同时受消息信息内容与协议对异常输入的稳健性影响；不度量互信息 | 正值表示对消息内容敏感 |
| `R_central` | 集中式参考差距 | Gap to centralized reference | 非因果；`π_central` 不是上界，可为负 | 正值表示仍落后于集中式参考 |
| `G` | 参考差距闭合率 | Reference gap closure | 辅助分析；仅当分母 95% 区间下界 ≥ 0.05 时给出；可大于 1 | 1 表示达到集中式参考 |
| `η_comm` | 通信效率诊断 | Communication efficiency (diagnostic) | 不进入主分；P0 以 `Δ_cut` 代替分子时标注"依赖度口径"；发射字节为 0 时不适用 | — |
| 扩容收益 | 规模收益（非协作增益） | Scale-up gain (not cooperative gain) | 资源不对齐；D3 `Ĝ` 归入此类 | — |

## 8. 提交配额与资源预算

### 8.1 提交流程与配额消耗时点

```
RECEIVED ──► SCANNING ──► VALIDATING ──► EVALUATING ──► SCORING ──► DONE
   │            │              │               │
   │            └──REJECTED────┘               └──FAILED（基础设施，退还配额）
   └──WITHDRAWN（RECEIVED、SCANNING、VALIDATING 可撤回）
   ▲                            ▲
   受理时在锁内预留配额单元      预留在进入 EVALUATING 时转为消耗；EVALUATING 起不可撤回
```

**预留规则**（R-LB-83）。配额检查与预留在同一把锁内完成，锁的粒度为（团队，Suite，划分）：受理时计算"窗口内已消耗单元数 + 未结预留数"，小于上限才创建预留并受理，否则拒绝 681；预留的窗口时刻取受理时刻（`reserved_unix_ns`），转为消耗后时刻不变。撤回、预检失败与 `T_f + 48 h` 评测截止释放预留；基础设施故障退还已消耗单元；VALIDATING → EVALUATING 迁移在同一把锁内核对预留仍然有效（未被释放、所属策略版本未失效），无效则 REJECTED 681，不得在无预留时消耗。这样，余额为 1 的团队并发提交 3 个 `holdout` 时，只有第 1 个获得预留，其余 2 个在受理时被拒绝。

| 事件 | 评测配额 | 预检计数 | 说明 |
|---|---|---|---|
| 受理时额度不足（已消耗 + 未结预留 ≥ 上限） | 不预留 | 不计 | 拒绝，原因码 681，`why = validation_quota` 或 `holdout_quota`（对应 AWR-06 §8.10 的 `QUOTA_EXHAUSTED`） |
| 受理成功 | 预留 1 | — | 写入审计日志（E-05） |
| SCANNING 失败（镜像、平台、大小、SBOM、许可） | 释放预留 | 计 1 | REJECTED 692 `scan` |
| VALIDATING 失败（冒烟：崩溃率 > 20% 或效用低于 `π_ind` 一半、握手或协议错误） | 释放预留 | 计 1 | REJECTED 692 `smoke`；冒烟只用公开种子，不泄露隐藏信息 |
| 撤回（EVALUATING 之前） | 释放预留 | 不计 | WITHDRAWN |
| 进入 EVALUATING | 预留转为消耗 | — | 写入审计日志（E-05） |
| 基础设施故障导致 FAILED | 退还 | — | 退还写入审计日志；泄露审计检出（`leak_detected`）不按基础设施故障退还，按 §10.2 分诊结论处理 |
| 资源违规（Suite `budget.policy = violation_invalidates`） | 已消耗 | — | 按 M32 规则计分，不退还；终态原因码 `BUDGET_VIOLATION` 仅在 Suite 选用"违规即终止评测"时使用 |
| 平台发起的追加评测（`Δ_perm`、X1、R-1、R-2、审计） | 不消耗 | — | 计入平台算力池 |

### 8.2 配额缺省值

| 配额项 | 缺省 | 计数范围 | 窗口 | 依据 |
|---|---|---|---|---|
| `validation` 评测 | 3 次 | （团队，Suite） | 滚动 7 × 24 h | ADR-D4-26；计数范围为本文设定（FB-06） |
| `holdout` 评测 | 1 次 | （团队，Suite） | 滚动 28 × 24 h | ADR-D4-26；同上 |
| 研究赛道评测 | 2 次 | （团队，Suite） | 滚动 28 × 24 h | 本文设定 |
| 同时活跃提交 | 3 个 | 团队（平台级） | 即时 | `py:bench/submissions.py` `ACTIVE_PER_TEAM` |
| 预检失败 | 10 次 | 团队（平台级） | 滚动 7 × 24 h；超限后 24 h 内拒绝新提交 | 本文设定，抑制以冒烟占用队列 |
| `dev` | 不限 | — | 本地运行，平台不执行 | §8.7 |

窗口以 UTC 时间戳滚动计算，不按自然周或自然月重置，避免在窗口边界连续提交。一个提交只针对一个划分；`holdout` 提交覆盖该 Suite 当前 Board Version 的全部成榜 `holdout` 场景集，对照赛道联评与主评测合计为一个配额单元；`validation` 提交每个配额单元只评测一个场景集（由提交者在 `scenario_sets[]` 中指定且只能指定一个），Ladder 反馈按（团队，分析组）分别维护。

`holdout` 提交在受理时即置 `visibility = board`，此后不可改（R-LB-84）；`validation` 提交不进入榜单，不提供可见性切换。全部 `holdout` 提交（含 REJECTED、FAILED、WITHDRAWN）的元数据公开（§5.2、§5.4）。

### 8.3 配额策略对象

配额由常量提升为两层策略对象（偏差 D-5）：平台级策略给出缺省与上限，Suite 级策略只能收紧、不能放宽。

| 字段 | 类型 | 说明 |
|---|---|---|

### 9.2 种子与承诺结构

种子生成、承诺计算与冻结工件由 M31 实现（R-M31-51 至 R-M31-54、R-M31-89；公式与编码以 M31 §7.7.4 与 ENC-01 至 ENC-05 为准，测试向量见 M31 §7.7.5）。本文在 AWR-06 §8.7 之上规定承诺的组织方式；下式与 M31 §7.7.4 逐项一致，二者如有出入以 M31 为准：

```
dec(x) = x 的十进制字符串（ENC-01，模式 ^(0|[1-9][0-9]{0,18})$，数值 < 2^63）
holdout 划分
 ├─ 轮换子集 H_a（区块集合 B_a；冻结时登记 retire_after_season）
 │    salt_a（256 位，拼接时为原始 32 字节）
 │    ranked seeds   ω_{s,1..m}，s ∈ H_a     → seed_set_commit_a     = hex(SHA-256(salt_a ‖ JCS([dec(ω) for ω in sorted_numeric(ranked)])))
 │    reserve seeds  ω_{s,m+1..m+r}，s ∈ H_a → reserve_seed_commit_a = hex(SHA-256(salt_a ‖ JCS([dec(ω) for ω in sorted_numeric(reserve)])))
 │    instances                              → instance_set_commit_a（M31 §7.7.4，含 dec(instance_seed)）
 │    block params                           → blocks[].params_commit（R-M31-49）
 └─ 轮换子集 H_b（区块集合 B_b） ……（同上，独立的 salt_b）
Board Version 冻结项：seed_set_commit = hex(SHA-256(JCS(sorted([seed_set_commit_a, seed_set_commit_b, ...]))))（汇总不加盐，R-M31-89）
                       instance_set_commit、reserve_seed_commit 同理
逐 Episode：seed_tag = HMAC-SHA256(salt_x, LP(utf8(episode_id)) ‖ LP(utf8(scenario_id)) ‖ u32be(seed_index) ‖ u64be(ω))，x 为场景所属子集
             （ENC-05：字符串为长度前缀 LP，序号为 u32be，种子为 u64be；M31 §7.7.3）
```

种子在任何 JSON 文本（含承诺原文、公开包、`--json` 输出）中一律为十进制字符串，在二进制拼接中一律为 `u64be`；不得以 JSON 数字表示。理由：RFC 8785 的 JCS 按 IEEE-754 双精度序列化数字，绝对值不小于 2⁵³ 的整数在不同实现间不能一致还原，现有 `py:sim/events/jcs.py` `jcs_number` 对此类整数直接抛出 `ValueError`（M31 F-15）。M32 F-40 与 R-M32-69 中的写法 `JCS(sorted(seeds))` 尚未按此编码更新（M31 §13 第 6 条已提出），本文在 FX-02 中重申。

| 参数 | 缺省 | 说明 |
|---|---|---|
| 轮换子集数 | 2 | 每子集约占场景数一半，按区块划分，子集之间区块不相邻 |
| 排名种子数 m | 5 | 与官方缺省"18 场景 × 5 种子"一致（pilot 后按 M32 规则冻结） |
| 保留种子数 r | 2 | 每场景 2 个，只用于 R-1 新种子复跑；18 个场景共 36 个保留单元，足以抽取 R-1 所需的 10 个 Episode |

单一盐覆盖整个种子集时，部分子集退役公开盐即暴露未退役子集的全部种子；因此每个轮换子集独立加盐（FB-04）。保留种子不承诺时，R-1 复跑所用种子无法事后验证（FB-05）。

### 9.5 密钥存储与访问控制

| 项 | 规定 |
|---|---|
| 存放 | 盐与种子只存于服务端密钥存储；不入仓库、不入日志、不经任何接口返回（沿用 D3 `config.json` 秘密种子只在服务端读取的约定，F4） |

### 9.6 Ladder 式反馈与展示精度

| 划分 | 规则 |
|---|---|
| `validation` | 对每个（团队，分析组）维护反馈值 L（整数百分点，初值为空）。新评测得到 `U` 点估计，按 §5.6 取整规则得到整数百分点 s：若 L 为空或 s > L + 2（即 ε = 0.02），则 L ← s 并返回 s；否则返回 L，并注明"本次结果未超过此前反馈值 + 0.02"。只返回 `U` 与名义样本量，不返回区间、场景分解、资源分解与 trace（Blum & Hardt，ICML 2015 [待核实页码]）；未取整的原始值只存于服务端，供探测监测（§10.6）使用 |
| `holdout` | 条目代表取最近完成的 `holdout` 提交（A-06，F3），不按"历史最佳"选择；`holdout` 提交受理即强制入榜（R-LB-84）；赛季 `active`、`frozen` 期间对非运营角色与公开快照以展示精度（0.01）发布 `U`、区间与 Δ 量；名次、名次区间、并列组与判定词正常发布；全精度在赛季 `closed` 后随归档发布 |
| 选择记录 | 每次 `holdout` 提交时冻结该团队此前在同一 Suite 的 `validation` 评测次数，写入条目的 `selection_record[]` 并在条目卡公开 |

AWR-06 §8.7 规定 Ladder 机制同时作用于 `validation` 与 `holdout`；但 `holdout` 的榜单展示采用"最近完成为代表"，若再叠加"只在超过此前展示值 ε 时更新"，即等价于"历史最佳为代表"，与 A-06 冲突。本文因此把 Ladder 的"超过阈值才更新"规则只用于 `validation`，`holdout` 以月度配额、取整展示与查询次数公开抑制自适应过拟合（FB-03）。

| SN-2 赛季资格取消 | 团队本赛季全部条目撤销，剩余配额作废 | 读取真值、旁路通信、场景硬编码、多账号探测 |

处置由复核委员会裁决（§11.5），裁决与理由以公告发布；SN-2、SN-3 的公告列明团队名称与违反的条款，不公开未经确认的指控。任何自动检测（泄露审计、旁路检测、静态审计）只产生"疑似"与分诊，不直接产生 SN 处置（§10.7）。

### 10.6 探测监测

`holdout` 每团队每 Suite 每 28 天 1 次，常规赛季内至多约 6 次、第一赛季至多 3 次；以 `holdout` 次数为样本单位的指标在赛季内几乎不可计算。v0.2 把监测的样本单位改为累计查询数与服务端保存的 `validation` 原始值，并为每项指标规定可计算条件与显著性要求：

| 指标 | 定义 | 可计算条件 | 触发阈值（占位值，预赛季数据后校准） | 依据 |
|---|---|---|---|---|
| M-1 | 同一 Suite 内，团队累计查询数（`validation` + `holdout`）与其代表条目 `U` 的 Spearman ρ；显著性以置换检验（10,000 次，置换种子由 `SHA-256("drone4d.lb.m1.v1" ‖ season ‖ suite ‖ week)` 派生，可复算）给出单侧 p 值 | 累计查询数 ≥ 3 的团队数 ≥ 8；不满足时周报注明"样本不足" | ρ ≥ 0.5 且 p < 0.05 | RK-09 (a) |
| M-2 | 代表条目的 `validation` 原始值均值与 `holdout` `U` 之差，减去校准基线 δ₀；δ₀ 与其标准差 σ₀ 由参考策略与官方基线（非自适应）在同一 Board Version 的 `validation`、`holdout` 上的成绩差估计 | 该团队在同一分析组有 ≥ 3 次 `validation` 评测与 1 个 `holdout` 代表条目；δ₀ 由 ≥ 6 个非自适应策略估计 | 差值 − δ₀ > max(3σ₀, ε)；δ₀ 未得出前以 2ε 为占位阈值并在周报标注 | RK-09 (b) |
| M-3 | 同一（团队，分析组）连续 ≥ 5 次 `validation` 评测的原始值每次提升均落在 (0, ε] 内（逐步逼近 Ladder 阈值的探测模式） | 该（团队，分析组）有 ≥ 5 次 `validation` 评测 | 成立 | RK-09 (c)；Ladder 机制 |
| M-4 | 静态审计发现特定地图或场景逻辑 | 前列提交的静态审计 | 成立 | RK-09 (d) |
| M-5 | 跨团队相同镜像摘要 | 每次受理 | 成立 | A-05 |

监测每周计算一次，结果进入运营周报；触发后进入人工审计，审计结论写入审计日志；监测触发本身不构成处置依据。M-1 至 M-3 的阈值在预赛季数据到手前均为占位值；其触发率与误报率以蒙特卡洛评估（AC-LB-17），误报率目标为每团队每赛季 ≤ 5%（本文设定）。

### 10.7 泄露检出的分诊与处置

M33 R-M33-61 把排名运行中 LA-01 至 LA-03、LA-05 至 LA-09 的检出与 LA-04 的确定性检出判为该 Episode `failure.infra`（`leak_detected`）、不重跑，并冻结该 Board Version 的新评测。泄露审计检查的是"不应到达 Agent 的信息是否到达"，其原因可能在平台（观测信封、层路由、交付实现的缺陷），也可能在提交（利用沙箱或接口缺陷主动获取）。v0.1 的"检出即判 SN-2"把全部检出归为提交原因，而"基础设施故障退还配额"又会使违规提交获得退还；整版冻结则使任一提交都能诱发全榜停评。本文规定如下（Episode 层的判定仍以 M33 为准，冻结范围的调整见 FX-01）：

| 阶段 | 规则 | 时限（目标值） |
|---|---|---|
| 检出 | 该提交立即隔离：停止其余 Episode 的调度，条目 `verification = under_review`，显示"审计中"标记；证据（相关 Episode 的全部层 trace、`leak_audit.v1`、运行清单）保全为永久保留；配额单元挂起，既不退还也不确认；写入审计日志与治理事件流 | 即时 |
| 分诊 | 评测员以参考提交与变异自检在同一 Board Version、同一场景上复现：参考提交同样检出，判平台原因；只有该提交检出，判提交原因候选；无法复现，判待定并进入人工调查 | 2 个工作日 |
| 分诊期内的评测 | 同一 Board Version 的其他评测照常进行，但分诊期内完成的评测标记为"待分诊确认" | — |
| 平台原因 | 冻结该 Board Version 的新评测（沿用 AWR-05 ADR-177 决策 (4) 的 `platform_audit` 与 M33 的冻结机制）；受影响提交与分诊期内完成的评测作废并退还配额；修复后以补丁或新 Board Version 发布（§12.3）；涉事团队的条目恢复 `provisional` 并免费重评 | 冻结公告即时 |
| 提交原因候选 | 不冻结整个 Board Version；配额不退还；由复核委员会按 §11.5 程序（含 10 个工作日答辩期）裁决，拟处置等级 SN-2；裁决前不公开团队名称 | 按 §11.4 |
| 待定 | 同"提交原因候选"，但调查期内允许涉事团队以新镜像继续提交其他 Suite；调查结论为平台原因时按平台原因处置 | 按 §11.4 |

LA-04 统计显著（M33 §6.8.2 第 2 类）只判 `suspect` 并进入调查队列，不隔离提交、不挂起配额，与 M33 一致。

### 10.8 条目包

M34 R-M34-46 规定 `drone4d bench verify` 与 `bench replay` 接受"平台导出的条目包（P1 由 LB 定义格式）"。条目包只针对公开划分上的运行（§10.4：冒烟运行与已退役转入 `dev` 的子集运行），格式如下（契约名建议 `drone4d.suite.entry_bundle.v1`，待 CT 登记，FX-04、FX-06）：

| 成员 | 内容 | 必需 |
|---|---|---|
| `bundle_manifest.json` | 包内每个文件的 `{path, sha256, bytes}`，按 `path` 的 UTF-8 字节序排序，以 JCS 写出，风格同 §12.4 `archive_manifest.json`；`bundle_sha256` 为其 JCS 字节的 sha256 | 是 |
| `entry.json` | `entry_id`、`board_version`、`season`、`submission_id`、`submission_digest`、`image_digest`、`track`、`scenario_set`、`split`、所含 Episode 列表、导出时刻（十进制字符串） | 是 |
| `rows.jsonl` | 该条目在包内范围的全部 `board_row.v1` 行（CT §5.4） | 是 |
| `run_manifest/<episode_id>.json` | 每 Episode 的运行清单（`drone4d.coord.run_manifest.v2`，CT） | 是 |
| `trace/<episode_id>/` | M33 格式的 trace；层范围按 §10.4（冒烟与已退役子集为全部层，`minimal` 级条目为该级别保留内容） | 视保留级别 |
| `instances.json` | 所用实例的 `instance_id` 与 `instance_sha256`；实例包本体从 `dev` 发布包另取，不重复打包 | 是 |
| `reveal_ref.json` | 已退役子集：E-16 公开包的引用与摘要，供复算 `seed_tag`；冒烟运行为 `null` | 是 |

| 项 | 规定 |
|---|---|
| 体积预算 | 单包 ≤ 2 GiB（目标值）；超出时按场景集拆分为多个包，各自带清单 |
| 校验 | `bench verify <bundle>` 依次校验：清单哈希；`rows.jsonl` 行的 `run_manifest_sha256` 与 `run_manifest/` 一致；运行清单的 `trace_sha256` 与 `trace/` 一致；有 `reveal_ref` 时按 R-LB-87 复算 `seed_tag`；任一失败以非零退出码返回并列出失败项 |
| 生成者与权限 | 平台导出；提交团队可下载本团队条目的包，赛季 `closed` 后任何人可下载已退役子集上的包 |
| 不含 | 未退役子集的任何内容、`validation` 运行、团队私有声明以外的个人信息 |

### 10.9 治理事件流与 `board.json` 重算

`board.v2` 中有一类字段不由 `rows.jsonl` 与榜单配置决定：`verification`、`notices[]`、`selection_record[]`、`eval_count`、`query_counts`、`first_listed_unix_ns`、`last_evaluated_unix_ns`、`published_unix_ns`，以及撤销（SN-1 及以上）后条目退出名次、并列组与分层的效果。为使 `board.json` 仍可逐字节重算，本文引入治理事件流作为第三个权威输入（E-17）：

| 项 | 规定 |
|---|---|
| 位置与格式 | 每个 Board Version 目录下的 `governance.jsonl`，只追加；每行 `{seq, kind, t_unix_ns, actor_ref, object{type, id}, payload, prev}`，`prev = sha256(JCS(上一行))`，首行 `prev` 为 Board Version 冻结记录（E-13）的摘要；`t_unix_ns` 为十进制字符串，由写入者记录，重算时只读取不生成 |
| 事件类别 | `verification_set`（复核状态变化，含报告引用）、`revoked`、`reinstated`、`notice_linked`、`quota_consumed`、`quota_refunded`、`selection_recorded`、`listed`（首次上榜）、`evaluated`（最近评测）、`snapshot_published` |
| 字段推导 | `verification`、`notices[]` 取对应事件的最新状态；`eval_count`、`query_counts` 为 `quota_consumed` 减 `quota_refunded` 的计数；`selection_record[]` 取 `selection_recorded`；`first_listed_unix_ns`、`last_evaluated_unix_ns` 取 `listed`、`evaluated` 事件的 `t_unix_ns`；`published_unix_ns` 取本次 `snapshot_published` 事件的 `t_unix_ns` |
| 撤销的效果 | `revoked` 的条目保留在 `entries[]`（显示"已撤销"），但不参与名次、并列组、名次区间、检验族与支配分层的计算；其余条目的这些字段随之重算 |
| 快照 | 每次发布 `board.json` 先追加 `snapshot_published` 事件，载明 `rows_count`（所用 `rows.jsonl` 前缀行数）与本事件的 `seq`；`board.json` 记录 `rows_digest`、`governance_digest`（至该 `seq` 的链尾摘要）与 `governance_seq` |
| 重算 | `verify_board(rows[:rows_count], config, governance[:governance_seq], board)` 以 JCS 规范字节比对（M32 R-M32-67 的扩展，FX-03）；赛季内按角色裁剪的治理事件不影响全精度产物的重算 |
| 与 Board Version 的关系 | 撤销、复核状态变化与公告引用不改变 Board Version 冻结项，不新建 Board Version，只产生新快照（§12.3） |

## 11. 结果复核与申诉

### 11.1 复核状态

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `provisional` | 已评分、未复核 | SCORING 完成 |

### 11.2 复核步骤

沿用 AWR-06 §8.10，本文补充执行方与时限：

| 步骤 | 内容 | 通过条件 | 执行方 | 时限（目标值） |
|---|---|---|---|---|
| R-1 新种子复跑 | 在保留种子上复跑 n_r = 10 个 Episode（§9.4） | M32 F-39 与 R-M32-70 的预测区间判据：`|μ̂_rerun − μ̂| ≤ z_{1−α_r/2} · sqrt(ŝ_o² + ŝ_r²) + ε`，α_r = 0.01，ŝ_o 为原估计标准误，ŝ_r 为原条目 Episode 层标准差除以 `sqrt(n_r)` | 评测员（流水线自动） | 发起后 3 个工作日 |
| R-2a 同等级复跑 | 同一硬件等级第二台机器复跑抽样 Episode | 等级 1b：事件哈希一致 | 评测员 | 5 个工作日 |
| R-2b 跨等级复跑 | 不同硬件等级机器复跑抽样 Episode | 同 R-1 的 F-39 预测区间判据 | 评测员 | 5 个工作日 |
| R-3 静态与行为审计 | 镜像静态审计、系统调用异常、高频动作成分、过敏反应 | 无异常或异常已解释 | 评测员 | 10 个工作日 |
| R-4 离线重算 | 由私有 trace 离线重算全部分量 | 与存储分量逐位一致 | 评测员（M33 工具） | 3 个工作日 |

v0.1 的 R-1、R-2b 判据"复跑均值落入原 95% 区间，或差值 < ε"只计原估计的误差，未计复跑 10 个 Episode 自身的抽样误差；M32 已以评审所设的 Episode 层标准差 0.25 估算其诚实条目误判率约 0.38，并改为 F-39 的预测区间判据（正态近似下误判率约 0.5%），以 MC-12 评估误判率（目标 ≤ 2%）与检出率（M32 §6.3 算例、RV-11）。本文采纳 F-39，判据参数随 `stats.version` 发布。

| 项 | 规定 |
|---|---|
| 执行方式 | R-1、R-2a、R-2b、R-4 与 R-3 并行执行；单条目全部步骤 ≤ 10 个工作日（R-3 为关键路径） |
| 必须复核 | 每个主榜赛道各分析组的前 3 名；申请论文或对外材料引用的条目（AWR-06 §8.10） |
| 滚动发起 | 赛季 `active` 期间，条目首次进入某主榜分析组前 3 名后，平台在 2 个工作日内自动发起复核；赛季 `frozen` 时仍为 `provisional` 的前 3 名由平台自动发起（§7.7）；复核算力计入审计与复核池 |
| 自愿申请 | 任何 `valid` 条目可申请，每团队每赛季每 Suite 至多 3 次（本文设定）；复核算力计入审计与复核池 |
| 不通过的处置 | R-1、R-2b 不通过：条目 `under_review`，评测员调查平台与条目两方原因；属平台原因则冻结该 Board Version 的新评测（沿用 AWR-05 ADR-177 决策 (4) 的 `platform_audit` 机制）；属条目原因则提交复核委员会 |
| 引用约束 | 论文与对外材料只可引用 `verified` 条目，并附"名次与区间未经选择校正"声明（AWR-06 §8.7） |

| AP-5 处置异议 | 对 SN-1 至 SN-3 处置有异议（二审） | 被处置团队 | 处置公告后 14 天内 |

### 11.4 申诉流程

```
FILED ──► TRIAGED ──► INVESTIGATING ──► DECIDED ──► CLOSED
   │          │                            │
   └─REJECTED_FORMAL（形式不符，可补正一次）  └──► APPEALED（AP-5 二审）──► DECIDED_FINAL ──► CLOSED
```

| 项 | 规定 |
|---|---|
| 提交内容 | 类别、涉及的条目与 Board Version、理由、证据（引用证据项编号与摘要） |
| 受理 | 5 个工作日内完成形式审查（TRIAGED 或 REJECTED_FORMAL） |
| 调查 | 评测员按需执行复跑、离线重算、审计；AP-1、AP-2 涉及的重跑不消耗提交团队配额 |
| 裁决 | 受理后 20 个工作日内作出；复杂案件可延长一次 10 个工作日并公告 |
| 裁决结果 | 维持；重算（评测器缺陷不改变已存储分量时为补丁版本，否则按 §12.3 处置）；重跑；标注；处置（SN-0 至 SN-3） |
| 赛季结算 | `T_f` 之后提起的申诉走快速通道（受理 3 个工作日、裁决 10 个工作日）；`T_c` 时未裁决的申诉不阻止赛季迁移到 `closed`，相关条目在归档中保持 `under_review`，裁决作为归档勘误发布（§7.7）；申诉不能推迟 `closed` 与下一赛季开启 |
| 公开 | 裁决以公告发布；AP-4 在指控未确认时匿名化处理被举报方 |

## 12. 版本化与归档

### 12.1 冻结项

Board Version 冻结项沿用 AWR-06 §8.9：`suite_digest`、赛道集合（含 §3.1 绑定属性的 `track_digest`）、场景集摘要、`instance_set_commit`、`seed_set_commit`、`score_version`、`evaluator_major`、`kernel_version`、`platform_digest`。本文增补 `season`、`season_digest`、`reserve_seed_commit`、各子集的 `retire_after_season`（§9.3）、`quota_policy_ref`（引用，不冻结配额数值）与 `golden_trace_digests`。治理事件流（§10.9）不是冻结项：撤销、复核状态变化与公告引用只产生新快照，不新建 Board Version。

### 12.2 标识

| 项 | 规定 |
|---|---|
| Board Version 标识 | `<suite_short>-<suite_major>.<suite_minor>-<season>-bv<NN>`，如 `taskalloc-1.0-s1-bv01`；满足 `py:bench/boardstore.py` 的 `_VERSION` 正则 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`（F4） |
| 补丁 | 不改变任何已存储分量的评测器修复不新建 Board Version，在变更日志中登记 `patch_level`；`board.json` 重算须逐字节一致 |
| `current` 指针 | 每个 Suite 一个 `current` 指针，指向当前赛季最新 Board Version；预赛季与历史赛季版本不得设为 `current`（沿用 D3 开发榜不得设为当前版本的约定） |
| D3 版本 | `board.v1` 既有版本名不变 |

### 12.3 变更处置

以 AWR-06 §8.9 为基准，采纳 M31 §7.9 的版本位细化（M31 已列为待 RFC 确认）：

| 变更 | Suite 版本位 | Board Version / 赛季 | 既有成绩 |
|---|---|---|---|
| 前端展示、文案 | 无 | 不变 | 不变 |
| 复核状态变化、撤销与恢复（SN-1 及以上）、公告引用、选择记录 | 无 | 不变；追加治理事件并发布新快照（§10.9） | 撤销条目退出名次、并列组、名次区间与分层，其余条目随之重算；变更日志登记 |
| 赛季 `closed` 后的复核、申诉、处置结论 | 无 | 不变；归档勘误（新版本 `archive_manifest.json`） | 按结论更正归档内容并公告 |
| 评测器修复且不改变已存储分量 | 补丁 | 补丁登记 | 不变，重算逐字节一致 |
| 新增诊断指标、新增场景集或赛道、开放新难度档或规模档、参考策略版本变化 | 次版本 | 新 Board Version | 迁入（新增指标补算或标"不适用"；参考策略变化时 Δ 族重算） |
| 实例集或种子集变化（轮换） | 次版本 | 新 Board Version，且只在赛季边界执行（§9.3） | 重评 |
| 评测器修复改变分量、主指标或评分规则变化、生成器主版本变化、删除 Family 或赛道 | 主版本 | 新赛季（只在赛季边界生效，R-LB-39） | 重评或归档 |
| 内核语义变化（黄金 trace 摘要改变） | — | 新赛季，`kernel_version` 主版本加一 | 重评 |

每次发布附变更日志：版本位、变更项、对既有成绩的处置、黄金实例与黄金 trace 摘要变化及理由（R-M31-69）。

### 14.1 原则
