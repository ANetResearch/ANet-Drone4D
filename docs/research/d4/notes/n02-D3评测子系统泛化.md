# D4 输入报告：D3 评测与排行榜子系统的泛化评估

范围：只读审阅。代码位于 `python/awr/bench/{eval/*,aggregate,boardstore,submissions,subworker,ctl,runner,spec_rules,api/board,api/submissions}`、
`python/awr/api/bench_main.py`、`packages/contracts/bench/*.schema.json`、`docs/05-D3-设计增补与决策记录.md` §5.6.5–5.6.9 与 ADR-147/150/182/183/191、
`apps/web/src/ui/lab/{LabBoardPage,LabSubmissionsPage,board.ts}`、`apps/web/src/net/bench.ts`。

## 0. 结论摘要

1. D3 的"统计与治理层"已经相当通用：赛道内分层自助法、成对差值 CI、统计并列、非支配层级、基线参考行、榜单版本冻结、提交状态机、容器隔离、真值隔离、`compose` 事后合成，**与 crop-handoff 任务语义基本无关**，可作为 D4 Suite/Leaderboard 框架的内核直接复用，约占现有评测与榜单代码的 55%–60%。
2. 耦合集中在三处：(a) 指标集合写死为 `("ec","eu","ao","ce")` 并贯穿 aggregate、compose、前端、score/board 契约；(b) 评测器 `evaluate_run` 以"关键事件 + 识别表 ident(u, p, k)"为唯一世界观；(c) 榜单配置是"单赛道、单事件、单 run_spec"（`subworker` 读取 `cfg["lane"]`、`cfg["run_spec"]["event"]["id"]`），不是"Suite → 多 Scenario/Instance"。
3. 泛化的主轴是把 **指标集合、任务实例集合、评测器插件、方向性（越大越好/越小越好）** 从常量提升为由 Suite 清单（manifest）声明的数据；同时把"赛道（lane）"一词拆分为 Suite、Track、Scenario Set 三层，避免 D3 中 lane 一词承载事件类型、研究任务、分轨三种含义。
4. 现有实现与设计文档存在 5 处偏差，D4 泛化前应先裁决并对齐（见 §5）。其中最重要的两处是：重采样随机数目前为 `sha256` 而非 `HMAC(K_board)`，种子位置存储为序号而非种子承诺；以及无效 Run 的处理在文档（记 0、不剔除）与代码（剔除）之间不一致。

## 2. 可直接成为通用框架的部分

可原样迁入 `awr.bench.core`（建议新名 `awr.suite` / `awr.board`）并仅做参数化的模块：

1. `aggregate` 中的重采样、成对 CI、并列、非支配、基线处理、`compose`：将 `METRICS` 常量改为参数 `metrics: list[MetricSpec]`，其中 `MetricSpec{id, direction, range, nullable}`；`dominates` 与降序排名按 `direction` 取反。
2. `boardstore`：`rows.jsonl` 追加式权威输入加重算产物的结构、版本冻结与 `current` 指针、`_listed` 的团队代表规则。冻结条件由"评分版本 + 赛道集合"扩为"Suite 清单摘要 + 评分版本 + 实例集合承诺"。
3. `submissions` 状态机、配额、可见性、`board_view`。
4. `subworker` 的阶段骨架与重跑策略；`scan_image` 的阈值移入 Suite 或平台策略。
5. 容器隔离参数集与线协议守卫、`spec_rules` 声明式规则引擎。
6. 前端排行榜表格的列驱动方式（`LfColumn` 已是数据驱动），只需让列来自 `board.metrics[]`。

## 3. 与 crop-handoff 耦合、需要抽象的部分

### 3.1 指标与评测器

- `evaluator.evaluate_run` 以 `scored_events(event_dir)`、`ident`（UAV × 演员 × tick 识别表）、`present`（磁带在场矩阵）为输入；EC/EU/AO/CE 的定义均建立在"事件窗口 + 识别"之上。CE 的增益 `Ĝ` 以覆盖 V(U) 对单机最优 V({u}) 的差计算，其思想（"团队相对最佳个体的增益"）与 design-r2 的 Δ_coop 同构，应提升为**通用的协作增益算子**：对任意任务指标 M，`Δ_coop(M) = M(fleet) − max_u M({u})`，并归一化到 `1 − 1/|U|`。这需要评测器支持"限制到子编队重算"，D3 以 `_restrict(ident, u)` 实现，D4 应成为评测器 SDK 的标准能力（子编队投影）。
- `eval/thresholds.py` 的 `TH`（h_px、vis、pad_s 等）与 `task.budget{distance_km_per_uav, comm_kb_per_uav}` 是任务特有的；其中**资源预算系数 `f_res`** 是通用概念（航程、通信字节），应抽象为 Budget 对象，由 Suite 声明维度与超额衰减函数。
- 安全（`safety.py`）以"演员胶囊最小间距、穿越即无效"实现，D4 的无人车/船/地面机器人需要通用的"体积碰撞/违规检测"接口。
- `ranked_valid`、`invalid_reasons` 已是通用的"有效性门"，但 `actor_penetration`、`physics_not_ranked` 为内嵌字符串，应由评测器插件注册。

### 3.2 任务与实例

- `task.v1` 的 `event_type` 枚举限定四类事件；`scored_event_types`、`report_types`、`known_targets`、`brief`、`altitude_envelope_agl_m` 均为事件任务字段。D4 的 TaskAlloc、CoopSearch、InfoShare、MAPF 等任务的"实例"是任务集、地图、通信图、障碍与故障序列，而非事件磁带。
- `run_spec.v1` 必填 `event` 与 `obs_level`；`fleet` 描述 UAV；物理档恒为 Realistic。D4 需允许"实例引用"（`instance`）代替 `event`，并允许异构 agent 集（`fleet` → `agents[]`，含 UGV/USV/固定传感器）。
- 秘密种子当前同时承担**实例随机化**（事件变体抽样、演员外观、目标先验）与**重采样随机化**两种功能，且 config 每榜只有一组 `seeds`，所有事件共用。D4 应把"实例集"与"种子集"分开承诺。

### 3.3 榜单配置与聚合

- `boardstore` 的 config 是单赛道：`subworker` 读取 `cfg["run_spec"]["event"]["id"]`、`cfg["lane"]`、`cfg["track_id"]`，一次提交只产出一个 lane 的 rows；设计文档（§5.6.7）规定的"所选赛道全部 test 事件 × 种子 × 重复"实际上没有实现多事件循环。
- `build_board` 的 `lanes[]` 带 `kind:"event_type"`，`tracks[]` 的字段（`obs_level`、`physics:"realistic"`、`mode:"exogenous"`、`appearance`）是 D3 轨道定义的全部内容，约束为 const。D4 的 Track 需要容纳协作档（C0–C3）、通信模型、物理档、接口类别（PettingZoo/插件/REST）与智能体类别。
- 并列判定只比较相邻条目；当 A≈B、B≈C 而 A 与 C 显著不同时，A、B、C 全部进入同一并列组（链式并列）。这对 D3 的少量条目影响小，对规模化的协作榜是方法学风险，建议改为"与组首比较"或层次聚类式的并列组。
- 非支配层级的计算复杂度为 O(n² · m) 的逐层剥离，且每个成对 CI 在重采样序列上计算；条目达到数百时需缓存与稀疏化。`_Pairs` 只缓存当前赛道的 boots 矩阵（10,000 × 4 浮点 / 条目），当指标数与实例数增大时需要关注内存。

### 3.4 其他

- `ctl board compose --weights ec=…,eu=…,ao=…,ce=…` 与 `score.v1.components` 枚举（`ec/eu/ao/ce/g_hat/f_res`）写死。
- 前端 `METRICS` 常量、i18n 键 `lab.board.metric.*`、`rank: ec.rank` 作为缺省排序键。
- `submission.v1` 的 `track` 与可选 `lanes[]` 是 D3 的二级结构，且镜像入口只有 `entry.cmd/env`；D4 的多智能体提交还需要"每个 agent 一个镜像还是同镜像多进程""集中式/分布式""是否使用平台提供的通信层"等声明。
- `subworker` 串行单线程处理，`smoke_s=20` 秒、种子 0 公开冒烟、DONE 后同步重算整榜（单条目耗时随榜单规模线性增长）。

## 4. 建议的通用抽象

命名以 `drone4d.suite.*` 为契约前缀（保持 D3 `drone4d.bench.*` 的兼容读取）。

### 4.1 层次关系

```
Suite (suite_id@version)
 ├─ Scenario Family[]        任务族（TaskAlloc, CoopSearch, ...）；有生成器与参数空间
 │    └─ Instance[]          具体实例 = (family, generator_params, instance_seed) -> 世界+任务+事件/障碍/故障 序列
 ├─ Split[]                  dev | public_test | hidden_test | stress
 ├─ Track[]                  比较单元的"赛制"：智能体类别 × 通信/协作档 × 物理档 × 观测档 × 预算
 ├─ Metric[]                 指标定义（方向、范围、归一化、评测器插件）
 ├─ Budget                   资源维度与超额衰减
 └─ Scoring                  聚合层次、重采样规则、排名/并列/支配规则、compose 权重表
Board Version = Suite 清单摘要 + Track 集合 + Split 清单摘要 + Instance 集合承诺 + 评分版本 + 评测器主版本 + 平台摘要
Leaderboard = ⋃ Board Version × Track × (Scenario Set) 的条目表
```

### 4.2 各抽象的定义与来源

| 抽象 | 定义 | 对应 D3 概念 | 变更要点 |
|---|---|---|---|
| Suite | 一套协同任务的版本化清单：家族、指标、轨道、划分、预算、评分规则；不可变 | 榜单 config + `run_spec` + `task` | 新增 `suite.v1` 契约；`suite_digest` 为清单规范化 JSON 的 sha256 |
| Scenario Family | 可参数化生成实例的任务族，声明 `generator`、参数空间、所需世界包、真值通道、评测器插件 | `event_type`（四类事件） | 事件任务变为 Suite `drone4d-event@1` 的 4 个家族，保持向后兼容 |
| Scenario / Instance | 一个可复现的评测单元：`instance_id`、`family`、`world_ref`、`params`、`instance_seed_commit` | `event` 变体 + 秘密种子 | 实例与重复种子分离；hidden 划分的实例参数不出评测域 |
| Split | `dev`（全公开）、`public_test`（输入公开、真值不公开，可无限次本地评测）、`hidden_test`（只在服务端、配额内评测）、`stress`（故障/扰动，非排名或独立排名） | dev/test | 与 D3 一致，增加 public_test 以支持自助调参 |
| Track | 赛制元组：`agent_class`、`coordination_level`(C0–C3)、`comm_model`(ideal/abstract/ns3)、`physics_tier`(L0–L3)、`obs_level`、`interface`(pettingzoo/plugin/rest)、`fleet_spec` | D3 分轨 | `board.tracks[]` 的 `const` 字段改为枚举并按 Suite 声明；不同轨道不混排的规则不变 |
| Metric | `{id, direction, range, unit, nullable, higher_is_better, evaluator, aggregation_level, requires_channels[]}` | EC/EU/AO/CE | 方向性与可空性成为一等属性；`dominates` 与排名据此处理；加 `kind: task|coop|resource|safety|robustness` |
| Coop Gain 算子 | `delta_coop(metric, baseline="best_single"|"random_k"|"centralized")` 通用化 CE 的 `Ĝ` | `ce.collaborative` | 评测器提供子编队投影；基线可选"最佳单体""同规模无通信""集中式上界" |
| Budget | `{dims:[{id, unit, per: agent|fleet|time, limit, decay}]}`，如 航程、通信字节、算力墙钟、LLM token | `task.budget` + `f_res` | 超额衰减函数声明化；预算违例进入 `ranked_valid` 或乘以资源系数二选一，由 Suite 指定 |
| Board Version | 冻结项扩为：`suite_digest`、`instance_set_commit`、`seed_set_commit`（HMAC）、`track_set`、`score_version`、`evaluator_major`、`platform_digest` | `board_version` | 冻结校验由"评分版本 + lane 集"改为"摘要集合"，旧版本只读 |
| Entry | `(board_version, track, family_or_scenario_set, entry_id)` 的聚合结果 | `(track, lane, entry_id)` | `lane` 保留为兼容别名，等价于 `scenario_set` |

### 4.3 评测器插件接口

```python
class Evaluator(Protocol):
    id: str; version: str
    metrics: list[MetricSpec]
    channels: list[str]                       # 需要的真值侧车通道，如 "tape", "ident", "tasks", "comm_log", "agent_state"
    def evaluate(self, run: RunView, instance: Instance, subset: AgentSubset | None = None) -> RunResult
```

`RunResult = {components: {metric_id: float|None}, ranked_valid: bool, invalid_reasons: [str], diagnostics: {...}}`；`subset` 支持 Δ_coop 重算。D3 的 `evaluate_run` 作为 `drone4d-event` 评测器的实现原样保留，`slim_evaluation` 泛化为 `slim(components, ranked, ranked_valid, invalid_reasons)`（已经与任务无关）。

### 4.4 聚合与排名的通用化

- 层次声明：`hierarchy: ["instance","seed","repeat"]` 加每层权重（等权或加权），默认等价于 D3 的"事件 → 种子 → 重复"。
- 重采样种子：`HMAC(K_board, entry_id ‖ board_version ‖ track ‖ scenario_set)`；`K_board` 由服务端密钥保管，不入仓库。
- 排名：每指标按 `direction` 排序；并列组改为"与组首比较"以避免链式并列；增加多重比较校正选项（Holm 或仅报告）。
- 非支配：基于方向化的点估计与成对 CI；增加 `epsilon` 容差避免因微小差异形成冗长层级。
- 条目表规模：`_Pairs` 对每个赛道缓存重采样矩阵；条目超过约 200 时改为只保存分位摘要与分块成对计算，并在 `board.json` 中增加 `stats{n_boot, method, version}` 以便复现。

## 5. 现有实现与设计文档的偏差（需在 D4 前裁决）

| 编号 | 偏差 | 文档 | 代码 | 建议 |
|---|---|---|---|---|
| D-1 | 重采样随机性与种子承诺 | `HMAC(K_board, …)`；`seed_set_commit` 为 HMAC | `sha256`；`seed_set_commit = sha256(逗号拼接的行内 seed)`，而行内 seed 是序号 k | D4 落实 HMAC；承诺对象应是真实种子集而非序号；否则承诺形同虚设 |
| D-2 | 无效 Run 处理 | `ranked_valid=false` 的 Run 全部分量记 0，不剔除 | 指标只按有效 Run 计算，占比 > 20% 则整条标无效 | 记 0 更利于抑制"靠无效运行挑选好成绩"；建议 D4 的 Suite 显式声明 `invalid_policy: zero|exclude` |
| D-3 | 多事件、多赛道提交 | 一次提交展开为所选赛道全部 test 事件 × 种子 × 重复 | `subworker` 只循环 `cfg.seeds`，事件固定为 `rs["event"]["id"]` | 在 Suite 化时一并实现"实例集 × 种子 × 重复"展开 |
| D-4 | 容器加固 | rootless + gVisor/seccomp、`--cpus 2`、`--memory 8g`、Trivy 扫描 | `containers.py` 缺省 cpus 1.0/mem 2 GB，无 `runsc`；`scan_image` 只检查存在、平台、大小 | D4 多智能体提交的资源与加固要求更高，应统一到 Suite 的运行策略 |
| D-5 | 配额 | 周配额、GPU 时间配额、同时排队 ≤ 2 | 仅 `ACTIVE_PER_TEAM = 3` | 引入配额策略对象（Suite 级与平台级两层） |

另有两项观察：`bench/score.v1` 的 `components` 枚举含 `g_hat`、`f_res`，说明 D3 已在契约层预留诊断分量；`ranked_row` 以字符串 `physics_not_ranked` 判定而非结构化的 tier 判定，D4 应结构化。

## 6. 契约变更草案

原则：新增 `suite.*` 契约族；`bench.*` 契约保持向后兼容（D3 榜单作为 Suite `drone4d-event@1` 的一个实例继续可读）；破坏性变更只发生在新增字段的必填化上，并随 `contracts` 主版本发布。

### 6.2 `bench/board.v1` → `board.v2`（保留 v1 读取）

- 新增顶层：`suite_id`、`suite_digest`、`instance_set_commit`、`stats{method, n_boot, version}`、`metrics[]`（MetricSpec 数组，替代隐含四项）。
- `tracks[]`：去除 `physics:const`、`mode:const`，改为枚举字段加 `coordination`、`comm_model`、`interface`。
- `lanes[]` 更名 `scenario_sets[]`（`kind` 取 `family | research | mixed`），保留 `lane` 作为别名一个主版本。
- `entries[].metrics`：由固定四键对象改为 `{<metric_id>: {value, ci95, rank, tie_group, repeat_delta}}` 的开放映射（`additionalProperties` 受 `metrics[]` 约束）。
- 新增 `entries[].reference_kind`（`baseline | oracle | random | single | centralized | null`），取代布尔 `baseline`。
- 新增 `entries[].coop{delta_coop, ci95}`，使"协作增益"成为每个条目的一等字段。

### 6.3 `bench/task.v1` → `instance.v1`

- `event_type` 枚举改为 `family`（字符串，受 Suite 约束）；`event_ref` 改为 `instance_ref`；`scored_event_types`、`report_types`、`known_targets` 并入 `family_params`（由家族 schema 校验）。
- `budget` 提升为 Suite/Instance 可覆盖的 Budget 对象。
- 保留 `brief`（面向 Agent 的可见描述）与"可见/隐藏"分层，隐藏部分带 `hidden: true` 标记，由序列化守卫剔除。

### 6.4 `bench/run_spec.v1`

- `event` → `instance`（二者择一，`exactly_one` 规则已有现成机制）；`fleet` → `agents[]`（异构）；增加 `track` 引用与 `interface`、`comm_model`、`coordination` 字段。
- `x-rules` 增加 Suite 兼容矩阵：如 `comm_model=ns3` 需要 `physics ≥ L1`；`coordination=C0` 禁止 `comm_model` 与 `outputs` 中的共享通道。
- `seeds`/`seed_count` 保留，新增 `instance_ids[]` 与 `repeat`。

### 6.5 `bench/submission.v1`

- 新增 `suite_id`、`track`（必填，沿用）、`scenario_sets[]`（取代 `lanes`）；`entry` 增加 `topology: "single_container" | "per_agent"`、`agents_per_image`、`declared_resources{cpus, mem_gb, tokens}`；增加 `signature` 与 `source_ref`（可复现来源，可选）。
- `result.lanes[]` → `result.scenario_sets[]`，每项含 `metrics`、`runs{total,valid,invalid,platform_rerun}`、`status`、`dominance_tier`。
- 状态机不变；增加终态原因码 `QUOTA_EXHAUSTED`（排队前拒绝）、`BUDGET_VIOLATION`（运行期，若 Suite 选用"违例即无效"）。

### 6.6 `bench/score.v1`

- `components` 枚举改为引用 Suite 的 `metrics[].id`；`weights` 保持可空；增加 `composite_scope: "none" | "track" | "suite"`，把 D3 悬而未决的"合成是否跨赛道"（Q-D3-19）显式化。

### 6.7 `bench/evaluation.v1`

- 顶层保留 `components`、`ranked`、`ranked_valid`、`invalid_reasons`（榜单只读取这四项）；任务特有块（`ec/eu/ao/ce/actors`）下沉到 `diagnostics.<evaluator_id>`；增加 `evaluator{id, version}` 与 `subset_results[]`（Δ_coop 所用的子编队重算记录）。

## 7. 排行榜产品层的建议

1. **协作智能排行榜 = Suite 列表 + 每 Suite 的 Track × Scenario Set 表 + 跨 Suite 的"协作画像"**。跨 Suite 不做加权总分（延续 D3 ADR-191 的立场），而是呈现每个条目在各 Suite 的非支配层级与 Δ_coop 区间（雷达/小多图，使用 lieflat 图表）。
2. **榜单版本 = Suite 版本冻结**：新增 Suite 不改变既有榜单；Suite 升级即新榜单版本；条目可按存储的分量重算后迁入（沿用 D3 "不需要重跑"的原则，限指标定义未变化时）。
3. **参考行类别**：随机、贪心、单体（best_single）、集中式上界（oracle）、已发表算法。Δ_coop 的比较基线随之成为榜单中的实体行，使"相对集中式上界的差距"可读。
4. **公开范围**：D3 明确榜单仅内部可见；D4 若要面向社区，应新增只读匿名接口与快照导出（含 `suite_digest` 与重算脚本），hidden_test 只回传指标，不回传观测与真值。
5. **可复现性**：`ctl board publish` 之外增加 `suite verify`（重算 rows 产出的 board.json 逐字节一致）与 `suite audit`（以固定实例重跑基线，对比历史指标，失败则冻结当前版本，沿用 ADR-177）。
6. **前端**：`LabBoardPage` 由 `board.metrics[]` 驱动列；新增 Suite/Track/Scenario Set 三级选择；条目详情展示按实例分解的指标与 Δ_coop 曲线（编队规模 N 的边际收益）。
