## 0. 总体结论（先读这一节）

1. 仓库里实际存在两条互不相交的运行栈，D4 的设计必须先承认这一点。
   - 栈 A（D1/D2 的 sim-core 栈）：`SimCore`（py:sim/runtime/main.py:338）单进程，250 Hz（`d1_250`）或 100 Hz（`sandbox100`）固定 tick，`FleetSim`（py:sim/fleet/fleet.py:119）以 SoA 批量积分，插件以 `register_stage` 登记 stage，内部经 zenoh `Bus`（py:runtime/bus.py）与 `StateRing` 通信；agent-runtime（py:agent/runtime/）以 asyncio + `SimScheduler` 运行 ANet 合同网。规模 1024 架机体 + 32 个识别物，确定性靠计数器 RNG、输入日志与重仿真。
   - 栈 B（D3 的 Bench Env 栈）：`BenchEnv`（py:agentsdk/env/core.py:70）纯 Python、100 ms 控制步 lockstep、PettingZoo Parallel 风格，物理经 `PhysicsTier`（py:phys/adapter.py）接 `KinematicTier` 或 `GzSimBackend`，观测经 `L1Model`/`L2Sensors`，通信经 `LinkModel`，Agent 在隔离容器内经 `wire.v1` 交互，评测经 `bench/eval`。栈 B 不 import `awr.runtime.bus`（已核对：`agentsdk/`、`phys/`、`bench/` 均无此依赖），也不使用 `FleetSim`。
   - D4 所需的"实验内协同"原型（点对点链路、消息、私有观测、动作守卫、决策时延、真值/Agent 可见分层记录）全部在栈 B 中，而不是栈 A。栈 A 提供栈 B 缺少的成熟件：批量实体运行时、动态目标、模型化感知、任务编排与分配器、离散时间表（SimScheduler）、输入日志/重仿真。
2. D4 内核建议以栈 B 为骨架泛化（因为它已经是"实验即环境"的形态），把栈 A 的 `FleetSim` 作为物理档 `fast` 接入 `PhysicsTier`（`run_spec.v1` 的 `physics` 枚举已含 `fast`，但 `BenchEnv._make_tier` 只实现 `kinematic` 与 `realistic`，其余抛 `ValueError`，见 py:agentsdk/env/core.py:120）。栈 A 的 stage 流水线与 Bus 不进入 D4 实验语义，只作为 `fast` 档的内部实现细节。
3. 六个抽象的现成度（自评，A 为已有可直接复用，C 为需新建）：

| D4 抽象 | 现成度 | 最强的现有件 | 最大缺口 |
|---|---|---|---|
| Agent / Entity | B | 栈 A 的 `FleetState`/`EntityTables`/`Roster`；栈 B 的 `_Agent` 与 `agent_config.v1` | 1:1 硬绑定 UAV；无 UGV/USV/固定传感器/无实体 Agent |
| Interaction / Link | B- | `LinkModel`（py:agentsdk/env/link.py:45） | 仅 UAV 点对点 + 固定自由空间公式；无交互图对象、无队列/信道竞争、无 Ideal/Abstract/NS-3 档位切换 |
| Message / Observation | B+ | `obs.v1`/`act.v1`/`wire.v1`、`obs_privileged.v1` | 观测信封与 UAV 绑定；消息无类型登记；无信息量/新鲜度度量 |
| Coordination Protocol / 插件 | C+ | `tasking.Allocator` 协议、`ContractNetAllocator`、`DroneAgent.step` SDK、`swarm/` 纯函数 | 没有统一的协同算法接口与问题实例抽象；PettingZoo 仅"风格"而非兼容 |
| 时空事件调度器 | C+ | 六处局部事件机制（见 §4）；`SimScheduler` 堆 | 没有统一事件队列与全序规则；栈 B 的投递量化到 100 ms |
| Trace | B | `EnvRecorder` 的 agents/truth 分层；`inputlog`；`tape`；MCAP | 无统一 trace schema；`run_manifest.v1` 只有 schema 没有写出者；无决策/信念轨 |

4. 三个专题的一句话结论：
   - Bus 与实验内通信网络：必须划成两个不同对象。Bus 是平台控制/遥测平面，墙钟、不可靠语义（`CongestionControl.DROP`）、不进入实验可观测量；实验内 Agent 消息一律走 `InteractionNetwork`，以仿真时间打戳、由键控 RNG 决定丢包与时延。栈 B 已天然满足，栈 A 的 agent-runtime 需要加防线（§3）。
   - 固定步长 SimCore 能否叠加离散事件调度：能，且已有五处先例。推荐"tick 边界 DES"：在每个物理步边界、物理推进之前按 `(t, priority, seq)` 全序弹出到期事件；事件时间保持精确值，状态读取用 `PoseHistory` 类插值而非"取下一步状态"（§4）。
   - 确定性：已有三层（计数器 RNG、输入日志/重仿真、位姿摘要）。D4 的缺口是：`run_manifest.v1` 无写出者、`agent_seed` 未下发、容器 Agent 的墙钟预算会把宿主速度带入结果、`GreedyAllocator` 的预算截断依赖墙钟（§5）。

### 2.1 Agent / Entity

D4 目标：区分决策者（Agent）与物理或数字实体（Entity）；一个 Agent 可控制 0 个、1 个或多个 Entity；Entity 类型覆盖多旋翼、地面机器人、船、固定传感器、边缘节点。

#### 现有可复用实现

| 内容 | 位置 | 说明 |
|---|---|---|
| 机体实体 SoA | py:sim/fleet/state.py `FleetState`（CAPACITY = 1024）；`FRAME_MULTIROTOR/FIXED_WING/VTOL`；构型列 `frame_kind` | 机体级状态的批量表示；构型只有三类空中机型 |

#### 缺口

- G-AE-1：Agent 与 Entity 在栈 B 里是同一个字符串。`EnvSpec.fleet` 的元素 `FleetEntry.uav` 同时是 Agent id 与机体 id（py:agentsdk/env/spec.py:20）；`run_spec.v1.fleet[].uav_id` 的模式为 `^uav-[0-9]{2,3}$`，上限 64 架。一个 Agent 控多个 Entity、一个无实体 Agent、多个 Agent 共享一个 Entity 都表达不了。
- G-AE-2：Entity 种类缺失。`FRAME_*` 只含三类空中构型；没有地面/水面运动模型，没有"无运动的固定传感器"。`KinematicTier` 与 `GzSimBackend` 的指令集（`TierCommand.kind ∈ velocity/goto/follow_path/orbit/hover/takeoff/land/kill`，py:phys/adapter.py:30）也是空中语义。
- G-AE-3：能力描述分散。栈 A 有 ANet 能力清单（ct:agent/capability*.json、py:agent/capabilities/），栈 B 有 `vehicle.limits`+`sensors` 的配置块，两者没有统一的 `capabilities` 声明，而 DynamicCoalition（r2 §五）要求"能力互补"的显式表达。
- G-AE-4：Entity 增删/故障/成员变化是 D4 一等事件（RobustCoord、DynamicCoalition 的"关键 Agent 故障"），栈 A 有 `roster`/`fleet/add|remove`/`fault/inject`，栈 B 的 `BenchEnv` 在回合内不支持增删，只有 `CRASHED` 终止。
- G-AE-5：`agent_seed` 在 schema 中有定义（ct:bench/agent_config.v1，`agent_seed ≤ 2^64-1`），代码中无任何下发者（全仓库 grep 仅命中生成的 `schema_types.py`）。

| 工作 | 估 | 备注 |
|---|---|---|
| 引入 `EntitySpec`/`AgentSpec` 二元模型（`AgentSpec.controls[]`、`observes[]`），`BenchEnv` 内部以 entity 表驱动 | M，约 3–4 人周 | `_Agent` 拆成 `AgentRT` 与 `EntityRT`；`run_spec` 增字段，旧 `fleet[]` 作为"一机一 Agent"的语法糖保持有效 |

| 回合内成员变化（加入/退出/故障）的调度钩子 | M，约 2 人周 | 依赖 §4 的统一事件队列 |

#### 与 D3 契约的衔接

- `agent_config.v1`：加法式扩展。新增 `entities[]`（该 Agent 控制的 Entity 引用与类型）、`capabilities[]`；`kind` 增补 `planner`、`sensor`、`ugv`、`usv`（字段是 `enum`，增加取值对旧消费者是破坏性的，需 `schema` 小版本号）。`uav_id` 保留为向后兼容别名。
- `run_spec.v1`：`fleet[]` 保留；新增 `entities[]` + `agents[]` 两个并列数组，二者互斥（`x-rules` 已有 `exactly_one` 求值器，py:bench/spec_rules.py，可直接登记互斥规则）。
- `board.v1.tracks[]`：`fleet_ref` 已是引用式，可指向新的"编队 + 异构构成"描述，无需改结构。
- `wire.v1`：每个 Agent 一个 Unix 套接字的现行模型（py:agentsdk/env/remote.py `SocketAgentHost`）按 Agent 而非按 Entity 建立，天然兼容 G-AE-1 的拆分。

### 2.2 Interaction / Link（交互与链路）

D4 目标：Agent/Entity 之间的通信边带有 `bandwidth, latency, jitter, packet_loss, range, reliability, cost`，随时间、位置、遮挡、天气、节点状态变化；至少三档网络：Ideal、Abstract、NS-3 协同仿真。

#### 现有可复用实现

| 内容 | 位置 | 说明 |
|---|---|---|
| 链路模型（栈 B） | py:agentsdk/env/link.py `LinkModel`（:45）：`_state`（:68）、`transmit`（:91）、`deliver_due`（:120） | 路损 `20lg d + 20lg f - 27.55`，NLOS +20 dB，余量 → logistic 丢包，速率 `1 Mbps·clip(margin/30, 0.05, 1)·bandwidth_scale`，时延 `10 ms + 8B/rate + U(0,20) ms + 区附加`；每机令牌桶；`(min,max,⌊t/1s⌋)` 对称缓存；逐条写 `net/records` |
| 外生通信扰动 | ct:event/tape.v1 `comms`；py:sim/events/tape.py `TapeReader.comm_zones_at`（:261） | 事件磁带携带通信区（`extra_loss`、`extra_latency_ms`、`bandwidth_scale`、多边形），`LinkModel._state` 已消费 |
| 键控延迟（栈 A） | py:agent/anet_mock/relay.py `latency_s`（:28）：`SeedSequence([world_seed, 5, blake2b(key)])`；`MockRelay`（:35） | 延迟只取决于消息键（`ix/rt`、`ix/upd/n`…），与到达顺序无关；`zero_latency` 给出 Ideal |
| 网络协议缝（栈 A） | py:agent/runtime/network.py `AgentNetwork` Protocol（register/find/delegate/updates/result/cancel）；py:agent/anet_mock/network.py `MockNetwork`（:75）；py:agent/anet_bridge/network.py `AnetDaemonNetwork` | 同一协议下 Mock（仿真时间）与真 ANet（墙钟）两实现并存，是"网络档位可替换"的先例 |
| 通信预算 | ct:bench/run_spec.v1 `comm{enabled, bucket_Bps, burst_B, msg_max_B, model}`、agent_config `comm`；py:agentsdk/env/link.py `CommCfg.model = "fspl-nlos@1"` | `model` 是带版本的字符串 id，扩展点形态已有 |

说明：py:sim/safety/link.py `LinkMonitor`（GCS 席位链路、agent 链路心跳阶梯）与 py:sim/tasking/relay.py `RelayController`（目标接力监控）都不是 Agent 间通信网络。前者是安全监视，后者是"目标交接"的任务逻辑，D4 不应复用二者的名字或概念。

#### 缺口

- G-IL-1：没有交互图对象。`LinkModel` 在每次 `transmit` 时按 `(src, dst)` 现算链路状态，不存在可查询、可记录、可作为问题输入的"当前拓扑"（邻接、分区、连通分量），而 InfoShare、Connectivity、RobustCoord 都以拓扑为研究对象。
- G-IL-2：只有 UAV-UAV 点对点；没有广播介质、多跳路由、地面站/边缘节点端点、Agent-传感器链路的差异化模型。`msgs[].dst` 只接受 `"*"` 或 uav id（py:agentsdk/env/link.py:91-97，ct:bench/act.v1 `OutMessage`）。
- G-IL-3：容量模型单薄。令牌桶限发送端，链路自身无队列、无排队时延、无信道竞争；时延的传输项 `8B/rate` 之外没有排队项，大消息和小消息在同一链路上互不影响。
- G-IL-4：网络档位无切换点。`model` 字符串只有 `fspl-nlos@1` 一个实现，`LinkModel` 内部写死；Ideal、Abstract、NS-3 三档没有公共接口。
- G-IL-5：链路状态的时间粒度。缓存键 `⌊t/1s⌋` 使位置变化在 1 s 内不更新视线；`transmit` 用调用时刻 `self.k` 的位置 `pos`，而不是 `apply_tick` 时刻（py:agentsdk/env/core.py:`_advance` 中 `pos = {u: self._row(u)[0:3]...}`），在 `lat_ticks > 1` 或追帧时存在轻微因果偏差。
- G-IL-6：规模。`pending` 是列表，`deliver_due` 每 tick 全表过滤并排序，O(P) 每步；64 机以上的广播密集场景会成为热点（估，未实测）。
- G-IL-7：键空间。链路 RNG 键 `(seed, 20, src_no·256 + dst_no, msg_seq, ch)`（py:agentsdk/rng.py），隐含 `src_no, dst_no < 256`；而 ct:rt/rng_streams.json 对流 20 的文字描述是六元键 `(seed, 20, src_no, dst_no, msg_seq, ch)`，二者不一致，扩到非 UAV 端点后需重新定键。

#### 改造代价

### 2.3 Message / Observation（消息与观测）

#### 缺口

- G-MO-1：观测信封与 UAV 绑定。`obs.v1` 的 `nav`（位置/速度/姿态/电量）、`status.mode ∈ landed/airborne/failsafe`、`ground_hint`、云台与相机配置都是空中机体语义；固定传感器、地面车没有对应字段。
- G-MO-2：消息无类型登记。`topic` 是自由字符串，载荷是不透明 bytes，平台只能计字节数；"最小任务充分信息"研究（r2 方向 B）需要按信息类别（原始观测/目标状态/任务摘要/意图）统计成本，目前只能靠研究者自行约定 topic。
- G-MO-3：无信息新鲜度/一致性度量。平台不知道一条消息承载了什么世界信息，无法计算"信息年龄"（AoI）或 Agent 间分歧。
- G-MO-4：Belief 完全在 Agent 内部。这符合"不替研究者做融合"的原则，但持续认知分歧（r2 方向 C）需要可比较的 Belief 导出通道。现有 `report`（带证据的语义断言）是一个出口，但它是为事件上报设计的，不是 Belief 快照。
- G-MO-5：观测延迟。传感器采集到交付的延迟在栈 B 只有"决策时延 τ"一项；传感器自身的曝光、处理、传输延迟没有显式模型（L2 帧带曝光中点时间戳，但交付时刻等于 tick）。
- G-MO-6：`act.tau_ms` 被忽略。`act.v1` 与 `agent_config.decision.mode = per_step` 暗示 Agent 可在每步声明自己的决策时延，但 `BenchEnv._settle` 只读 `spec.decision.lat_ticks()`（py:agentsdk/env/core.py:222-228）；`rg tau_ms py/awr/agentsdk` 无其他读取点。
- G-MO-7：真值泄露面审计缺失。栈 B 的约束靠 schema 白名单与目录分层（`agents/` 与 `truth/`）保证，尚无自动化的"Agent 可见字节集合 ⊆ 白名单"检查（`agents/<uav>/obs.sha256` 记录了交付观测摘要，具备审计基础）。

- G-ES-1：没有统一事件队列和统一全序规则。E1–E6 的同刻次序分别由 stage order、`seq`、列表顺序决定，没有跨机制的 `(t, priority, seq)` 约定。
- G-ES-2：事件类型无统一登记。D4 需要的事件类（消息投递、任务到达、链路变化、故障注入、成员变化、定时器、观测就绪）没有共同的类型/载荷/记录格式。

- G-ES-5：调度器本身不可序列化。`SimScheduler._heap` 里的回调是闭包，checkpoint（py:sim/runtime/ckpt.py）不包含它；恢复后 agent-runtime 通过"非终态任务置 input-required（interrupted）"重建（py:agent/runtime/app.py 状态机说明），不是逐位复原。D4 要求事件可复现，意味着事件须是"数据"而非闭包。

## 3. 专题：内部 Bus 与实验内 Agent 通信网络的边界

### 3.1 现状

- `Bus`（py:runtime/bus.py）是全仓库唯一 `import zenoh` 的模块（lint：tools/lint/check_py_imports.py）。契约要点（文件头注释）：所有发送 `CongestionControl.DROP`；可靠性由事件 `seq` + `_replay`、命令 `cid` 幂等 + 重试、状态取最新值保证；`call` 默认 1 s 超时 + 2 次重试；端点只允许回环地址；`LocalBus` 与 `ZenohBus` 同接口。key 空间在 ct:bus/keys.json（56 项，如 `ctl/{producer}/cmd`、`evt/sim-core/*`、`state/sim-core/*`），QoS 分级 `INTERACTIVE_HIGH` 等。
- `StateRing`（py:runtime/statering.py）是 `/dev/shm` 的 mmap seqlock 单写多读环，传输机体 `Full64`/`Lite32` 状态，不是消息通道。
- 栈 B 完全不使用 Bus 或 StateRing（已核对）。实验内通信由 `LinkModel` 在 `BenchEnv._advance` 中以仿真时间投递；Agent 与 Env 之间用 `wire.v1`（Unix 套接字，每 Agent 一条）。
- 栈 A 的 agent-runtime 通过 `SimBridge`（py:agent/runtime/bridge_sim.py）经 Bus 访问 sim-core（`ctl/sim-core/estimate|lease|cmd|query`、`svc/geo/height`、事件订阅 `evt/sim-core/*`、StateRing LOSSY 读者）；Agent 之间的"网络"是 `AgentNetwork` 的 Mock（`SimScheduler` 上的键控延迟）或真 ANet（墙钟）。

### 3.2 边界定义（建议作为 D4 设计约束）

| 通道 | 归属 | 时间基准 | 对被测算法可见 | 是否可被实验变量化 | 例 |
|---|---|---|---|---|---|
| Agent ↔ Agent 消息 | 实验内交互网络（`InteractionNetwork`） | 仿真时间 | 是（延迟、丢失、顺序、容量） | 是（`comm.model` 及参数、外生通信区） | `msgs[]` → `inbox[]`；`MockNetwork.delegate` |
| Env → Agent 观测 | 传感器模型 | 仿真时间 + 声明的传感器延迟 | 是（内容与时刻） | 是（噪声、延迟、视场） | `obs.v1` |
| Agent → Env 动作 | 执行通道 | 仿真时间 + 决策时延 τ | 是（生效延迟、回执） | 是（`decision.*`） | `act.v1` + `apply_tick` |
| 平台内部控制/遥测 | Bus | 墙钟 | 否 | 否（但是资源争用会间接影响 RTF） | `ctl/*`、`evt/*`、`state/*` |
| Agent ↔ Env 的承载（容器套接字） | Harness | 墙钟 | 否（但不得泄露墙钟进入仿真） | 否 | `wire.v1` |
| 观察者（UI、录制器、Rerun） | 旁路 | 墙钟/仿真 | 否 | 否，且不得反向扰动仿真 | 订阅 `evt/*`、StateRing |

### 3.3 规则

- R-B1：实验内 Agent 消息不得经过 zenoh Bus 传输。栈 A 的合同网委派是例外情形的历史产物（`MockNetwork` 在 agent-runtime 内部以 `SimScheduler` 投递，并不经 Bus；真 ANet 才走 HTTP），D4 若在栈 A 一侧复用合同网，须明确其网络档位属"Abstract（Mock）"，并禁止选用 `AnetDaemonNetwork` 参与排名。
- R-B2：任何通过 Bus 完成的"控制往返"（例如 agent-runtime → sim-core 的 `cmd`）在实验语义里必须被建模为固定的仿真时间延迟（决策时延 τ / `apply_tick`），而不是实测墙钟往返。栈 A 的先例：`BatchCtl.lat_ticks`、`StagedCmd.apply_tick`、输入日志的 `apply_tick`。
- R-B3：Bus 的"尽力而为"语义（`DROP`、重试）不能进入实验。若实验需要丢包，必须由 `InteractionNetwork` 的键控 RNG 产生，可复现。
- R-B4：墙钟不得进入仿真结果。已知例外：`SimCore` 对 Velocity 流 250 ms 墙钟看门狗（py:sim/fleet/stages/ingest.py:1 头注释），属栈 A 的设计；D4 的 `fast` 档不使用该路径。
- R-B5：旁路订阅者不得拥有写权限（UI 的 `viewer_queue` 等），录制器只读。
- R-B6：资源争用对 RTF 的影响不是确定性问题，但会触发"追帧限速"（`rtf_limited`，py:sim/runtime/clock.py `steps_due`）。D4 批量模式须使用无墙钟节拍的路径（`batch.py`/`BenchEnv` 的 lockstep），实验结果与 RTF 无关。

### 3.4 需要新增的防线（代价小）

- 静态检查：在 `tools/lint/check_py_imports.py` 的规则里增加"`awr.agentsdk`、`awr.phys`、`awr.bench` 不得 import `awr.runtime.bus`"（目前靠约定，已核对成立）。
- `InteractionNetwork` 在构造时拒绝接受 Bus 对象（类型约束）。
- trace 中的消息记录强制带 `t_send_ns`、`t_recv_ns`（仿真时间）与 `network_id`（档位 + 版本），墙钟字段单列并标注 `wall_*`。

## 4. 专题：固定步长 SimCore 能否叠加离散事件调度

### 4.1 结论

能。仓库已有五个独立的先例（§2.5 的 E1–E5），且各自带回归测试或确定性约束。D4 不需要放弃固定步长物理，需要的是把这些先例收拢为一个共享的事件队列，并定下三条规则。

### 4.2 推荐结构："tick 边界 DES"

1. 物理仍按固定步长推进（`FleetSim.step`、`PhysicsTier.advance`、gz 锁步）。
2. 事件队列保存精确时间戳（ns）的数据化事件；每个物理步 `(t_k, t_{k+1}]` 开始之前，弹出所有 `t_due ≤ t_{k+1}` 的事件，按 `(t_due, prio, seq)` 依次处理；处理过程可产生新事件，只要 `t_new ≤ t_{k+1}` 则同轮继续弹出（`SimScheduler.advance_to` 的 `while _pop_due` 即该语义）。
3. 事件处理可修改的只有"下一步将被物理消费的输入"（指令、环境参数、任务表、链路状态、收件箱）；不得直接改写本步已积分的状态。这与 E1（`apply_tick = tick + 1`）和 E4（"下一步边界生效"）一致。

### 4.3 三条必须定下的规则

- 规则 T1（全序）：同一时刻事件的次序为 `(t_ns, prio, seq)`，`prio` 按事件类型登记（建议：fault < membership < link_change < task_arrive < msg_deliver < timer < obs_ready），`seq` 为入队单调序号。`SimScheduler` 已是 `(t_due, seq)`，增加 `prio` 即可。
- 规则 T2（因果）：消息投递时刻 `t_recv = t_send + delay`，其中 `delay > 0`；接收方在 `t_recv` 之前不得读取该消息。栈 B 的实现满足（`deliver_due(t)` 只取 `t_recv ≤ t`），并因控制步量化只会更晚可读；D4 需要在 trace 中同时记录 `t_recv_ns` 与 `visible_k`（Agent 实际可读的控制步），使"量化延迟"成为显式量。
- 规则 T3（亚 tick 读取）：事件在 tick 内的精确时刻 `t_e`，其处理函数若需读取世界状态，使用 `PoseHistory`（py:phys/pose_history.py `PoseHistoryBuffer.slice/last_sample`，已用于相机曝光中点采样）按 `t_e` 插值，而不是读取 `t_{k+1}` 的状态。否则回调看到的世界比其时间戳晚至一个 tick（栈 A `SimScheduler` 的回调在 `now == t_due` 时读取 `StateRing` 最新帧，存在这种偏差，量级为 4/10 ms，对任务分配无影响，对高速交会的通信研究需要显式声明）。

### 4.4 与现有时钟档的适配

| 栈 | 物理 tick | 控制/观测节拍 | 事件时间粒度（建议） |
|---|---|---|---|
| 栈 A `d1_250` | 4 ms | 5 Hz 感知、10 Hz 目标等（stage 多速率） | ns，tick 边界处理 |
| 栈 A `sandbox100` | 10 ms | 同上 | ns，tick 边界处理 |
| 栈 B `kinematic`/`realistic` | 4 ms 步（gz 与运动学），100 ms 控制步（`TICK_MS = 100`，py:agentsdk/env/core.py:`TICK_MS`） | 10 Hz | ns；对 Agent 的可见节拍仍为 100 ms，可选事件驱动唤醒 |
| 事件磁带 | 100 ms（`TICK_NS = 100_000_000`，py:sim/events/tape.py） | — | 磁带自身以 100 ms 为定点，演员插值读取可到任意 ns |

### 4.5 风险

- 事件风暴：广播密集场景下一个控制步内可有 O(N²) 个投递事件；`EventQueue` 须批量弹出，并避免每个事件触发 Python 回调（沿用栈 A "回调线程只做入队"的纪律）。
- 回调重入：处理函数产生同刻新事件时的递归深度须有上界（`SimScheduler.advance_to` 有 `drain_loop` 上限 `_DRAIN_MAX = 10_000`）。
- 暂停与单步：栈 A 的暂停语义靠 `SimClock` 状态；`EventQueue` 本身不读墙钟，天然随仿真时间冻结。
- asyncio 依赖：`SimScheduler` 基于协程，`drain_loop` 窥视 `loop._ready`（私有属性，py:agent/runtime/clock.py:`drain_loop`），升级 Python 时有风险。D4 的 `EventQueue` 应是纯同步数据结构，协程适配器另置。
