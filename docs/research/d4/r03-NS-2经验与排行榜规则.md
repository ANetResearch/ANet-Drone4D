## 1. 结论摘要

1. NS-2/ns-3 成为标准平台的壁垒不在"仿真得真"，而在"实验可被他人逐项复核、逐项替换"：脚本化实验、稳定的协议接口、标准化的拓扑与流量模型、单一离散事件内核、trace 与后处理分离、随机流与重复管理、社区贡献生态七项要素缺一不可。
2. 应迁移的是实验纪律：声明式配置、Attribute 式参数登记、显式运行上下文、固定步长与离散事件的混合内核及其同刻排序规范、窄接口的对象分层、真值与 Belief 的物理隔离、Trace Source/Sink 与唯一规范 trace 格式、按随机源命名的独立流、Run Manifest、黄金 trace 回归、内核版本与赛季绑定、贡献分级。
3. 不应照搬：双语言绑定、全局单例与隐式默认种子、未标注假设的默认模型、深度耦合的内部 API、把仿真保真度等同于结论可信度、文本行 trace 加 awk、把平台与某一类求解器绑定。
4. 排行榜的主要失败模式有五类：择优发布与样本不对等（Chatbot Arena）、测试集泄露与饱和（Open LLM Leaderboard）、对基准选择的敏感（Benchmark Lottery）、不同算力与方法量级混排（NetHack Challenge、League of Robot Runners）、条件元数据缺失（Papers with Code）。
5. 协作智能排行榜须在 D3 已有设施（容器化提交、提交状态机、自助法置信区间、支配分层）之上补齐：留出集与秘密种子承诺、提交配额与评测次数公开、按场景分层的层次自助法与真正配对、多重比较校正与实际意义阈值、资源对齐的协作贡献对照、按资源预算划分的赛道、赛季与版本冻结、结果复核与审计。
6. 榜单是平台的产物而非目标：每赛季回顾是否在鼓励无关方向的爬升，并保留接收负面结果与协作失效诊断的研究赛道。

## 2. NS-2/ns-3 成为标准平台的七项要素

| 序 | 要素 | 说明 |
|---|---|---|
| 1 | 可复现的脚本化实验 | 一次实验即一个脚本文件加一个随机种子，他人可原样重跑；论文附脚本成为领域惯例 |
| 2 | 协议即模块，接口稳定 | 新协议只实现 Agent/Connector 等基类即可接入既有拓扑、链路与流量；AODV、802.11 等参考实现因此成为共同基线 |
| 3 | 标准化的拓扑、流量与信道模型 | 有线与无线节点、队列、CBR/FTP/Telnet 流量发生器、随机移动模型、误码模型均内置，论文之间因此可比 |
| 4 | 离散事件内核简单且唯一 | 单一事件链加虚拟时钟；调度器可替换（List、Heap、Calendar、Real-time，书 4.3），事件有唯一 ID；语义极简才易于验证 |
| 5 | trace 与后处理分离 | 仿真只产出 trace，统计与可视化（nam、awk 脚本）在外部完成 |
| 6 | 随机数的流与重复管理 | 书 15.2 区分确定性、单流、多流三种设置，缺省种子固定为 1，独立重复须显式改种；ns-3 以 MRG32k3a 的流、子流与 `RngRun` 管理，推荐固定种子、递增运行号，并要求发表时披露种子与重复方法 |
| 7 | 社区贡献生态 | 模块以源码形式发布、可交叉引用；ns-3 增加测试套件、持续构建与 app store，形成可持续的贡献闭环 |

## 3. 迁移规则

### 3.1 脚本化实验与组件化

NS-2 的双语言结构（OTcl 配置、C++ 执行；书 3.1："C++ 运行快但改动慢，OTcl 运行慢但改动快"）带来类绑定与变量绑定的样板代码、调试须穿越两个解释域、编译等待等代价。ns-3 去掉 OTcl，改为纯 C++ 加 Python 绑定，并以 Attribute 系统承担配置职责。

| 规则 | 内容 |
|---|---|
| R1 | 实验以版本化的声明式配置（YAML/JSON）为主、Python 为辅；不引入第二种运行时语言；配置层与执行层的边界是数据（schema），而不是语言绑定 |
| R2 | 建立类 Attribute 的统一参数系统：每个可配置项带名称、类型、缺省值、取值范围与文档，可枚举、可序列化，并在运行记录中完整回显；配置不得存在于代码常量中 |
| R3 | 不照搬全局单例（`Scheduler::instance()`、`defaultRNG`）；全部状态属于显式运行上下文，以支持同进程并行多个实验 |
| R4 | 不要求用户写底层语言才能扩展；扩展点以 Python 插件与进程外协议为主，性能关键路径由内核提供 |

### 3.2 离散事件调度器

NS-2/ns-3 的内核是单一时间有序事件队列；无人系统仿真通常是固定步长的连续动力学，而协同研究的对象（消息、任务到达、感知事件、固定外生事件）天然离散。

| 规则 | 内容 |
|---|---|
| R5 | 混合内核：连续动力学按固定步长积分，通信、任务、观测与决策触发以离散事件调度；两类时钟共享同一虚拟时间轴，事件排序规则（时间、阶段、全局序号）写入规范并作为一致性测试对象 |
| R6 | 事件顺序完全由配置与种子决定，不依赖线程调度或墙钟；同时间戳事件有确定的稳定排序 |
| R7 | 调度器实现可替换，但对外语义（顺序、取消、时钟）不可变；"实时 / 硬件在环"模式只作演示，不进入排行榜 |
| R8 | 事件处理器不直接发布全局副作用；Agent 只能经受限接口与世界交互（动作、消息、请求观测），便于记录与回放 |

### 3.3 协议模块化与标准接口

NS-2 的 Agent/Connector/NsObject 与 Node–Link–Classifier 分层使协议可替换，但内部耦合重，新模块开发需同时修改 C++、OTcl 与绑定三处。ns-3 以 Node、NetDevice、Channel、Application 四个对象加 helper 简化。

| 规则 | 内容 |
|---|---|
| R9 | 核心对象采用 Agent–Entity 模型，并补齐与 ns-3 对应的分层：Entity（物理实体）、Sensor/Actuator（类 NetDevice）、交互网络（类 Channel）、Policy（类 Application）；每层只暴露窄接口 |
| R10 | 接口版本化：契约文件遵循语义化版本，破坏性变更伴随迁移说明与兼容窗口；参考基线与接口同版本发布，充当"共同基线" |
| R11 | 提供 Helper 层以一行配置构建常见组合；helper 不得隐藏影响结果的参数，其展开结果写入运行记录 |
| R12 | 世界真值与 Agent Belief 物理隔离：Agent 只能拿到观测档允许的内容，相当于网络仿真中"节点只能经链路收包"的约束 |

### 3.4 标准场景与任务流

NS-2 内置的拓扑生成、流量发生器与 random waypoint 移动模型使论文拥有共同背景；random waypoint 的稳态问题也表明"缺省模型"会被无批判地沿用。

| 规则 | 内容 |
|---|---|
| R13 | 建立标准库：世界包、编队配置、任务流（泊松、突发、周期、事件图驱动）、目标运动模型、故障模型；每项标注来源、参数、适用范围与已知局限 |
| R14 | 标准场景分为冒烟（分钟级，用于开发与持续集成）、标准（用于论文与榜单）、压力（规模与扰动）三档，参数网格固定并公开命名 |
| R15 | 缺省模型附"有效性声明"，说明其不反映的现实因素；榜单只使用经声明的场景，避免"缺省值垄断" |

### 3.5 Trace 与可视化

NS-2 的 trace 为文本行（书 14.3.5），后处理依赖 awk，格式长期自成一套、字段随协议不一致；ns-3 把 trace 重构为 Source/Sink 解耦，并提供 PCAP 与 ASCII 输出，使 Wireshark 等外部工具可直接使用。

| 规则 | 内容 |
|---|---|
| R16 | Trace Source/Sink：内核与模型在稳定命名路径上暴露 Trace Source，评测、可视化、日志作为 Sink 挂接，不修改模型 |
| R17 | 唯一规范 trace 格式（带 schema 版本的 JSON Lines，可转换为列式格式），字段含时间、事件类型、主体、客体、载荷摘要与因果前驱 ID |
| R18 | 因果字段是相对 NS-2 的增量：每个事件记录其触发事件，使"为什么该任务未完成"可追溯，服务于协作贡献分析 |
| R19 | 回放器以 trace 为唯一输入，不依赖仿真器在线；前端回放与榜单的"可复核回放"共用同一播放器 |
| R20 | 不全量开启 trace；缺省只开启评测所需最小集，其余按需启用，并报告 trace 开销 |

### 3.6 随机数与重复

| 规则 | 内容 |
|---|---|
| R21 | 每个随机源（任务到达、目标运动、感知噪声、通信丢包、Agent 内部）拥有独立命名流，由 `(master_seed, run_id, stream_name)` 确定性派生；新增随机源不得改变既有随机源的序列 |
| R22 | 评测协议规定重复数、种子集合与置信区间方法；单次运行的结果不得上榜 |
| R23 | 区分环境随机性与 Agent 随机性：环境流由平台控制，Agent 流由平台派生并下发、由提交方使用，以区分环境方差与算法方差 |
| R24 | 每次运行输出完整的 Run Manifest（版本、配置哈希、种子、世界包哈希、镜像摘要），作为结果的唯一凭据 |

### 3.7 验证套件

ns-3 的测试体系分为构建验证、单元、系统、示例（冒烟）与性能五类，由 test.py 统一调度，部分测试比对参考 trace，并有多平台持续构建；NS-2 时代缺少同等强度的回归体系，版本间结果漂移是长期问题。

| 规则 | 内容 |
|---|---|
| R25 | 同构的测试层次：单元（调度器排序、动力学、感知模型）、系统（端到端场景）、示例冒烟、性能基线（每步耗时与规模曲线） |
| R26 | 黄金 trace 回归：对标准场景保存参考 trace 摘要，任何内核改动若改变摘要，须在变更说明中给出理由并升级内核版本号 |
| R27 | 区分 Verification（实现是否符合规格）与 Validation（模型是否反映现实）；后者按保真度档逐档给出与真实或高保真数据的偏差报告，不把仿真精度默认为现实精度 |
| R28 | 评测内核版本与榜单版本绑定：内核语义变化即为新赛季，不与旧成绩混排 |

### 3.8 社区贡献机制

NS-2 以源码补丁方式贡献，质量参差，长期并存大量不再维护的第三方补丁；ns-3 增加贡献规范、维护者制度与 app store。

| 规则 | 内容 |
|---|---|
| R29 | 贡献物分级：Core（内核维护）、Contrib（经评审并通过测试套件）、Community（自行托管、登记元数据）；每个模块声明接口版本、依赖、许可、测试与引用方式 |
| R30 | 模块注册表记录兼容矩阵与最近验证日期，超期未验证自动标记为"过期" |
| R31 | 基线算法库作为一等公民：每个算法附论文来源、参数与复现差异说明，未复现到原文水平的须明示 |

### 3.9 不应照搬清单

1. 双语言绑定及其样板代码（R1–R4）。
2. 全局单例与隐式缺省（`defaultRNG`、缺省种子为 1），易使不同实验无意共享状态。
3. 以未标注假设的缺省模型作为事实标准（R15）。
4. 模块间深度耦合的内部 API。
5. 把仿真保真度等同于结论可信度：协同研究需要的是可控、可解释的抽象，因此观测、物理、网络三条保真度轴应独立配置。
6. 以文本行 trace 加 awk 作为唯一分析手段。
7. 把平台与某一类求解器绑定。

## 4. 排行榜案例：成功与失败

| 案例 | 要点 | 核对 | 对协作智能排行榜的启示 |
|---|---|---|---|
| Chatbot Arena | The Leaderboard Illusion 指出：私下测试多个变体并择优发布、选择性披露，专有模型获得更多对战样本（Google、OpenAI 分别约 19.2%、20.4% 的数据，83 个开放权重模型合计约 29.7%），额外数据可带来对 Arena 分布最高约 112% 的相对提升 | 已核对摘要 | 提交次数与变体数量受限并公开；各参赛者评测样本量对等；不得撤回成绩 |
| Open LLM Leaderboard | 2024 年第二版因题目泄露进训练集、分数逼近人类水平而重做；2025 年 3 月宣布退役，理由含"鼓励向无关方向爬升" | 已核对 | 榜单有寿命，须预设赛季与退役机制；测试集随时间轮换 |
| Benchmark Lottery（Dehghani 等，2021） | 排名对基准选择高度敏感，单一基准上的第一不代表整体最优 | 既有知识 | 榜单必须是多场景套件，并报告排名稳定性 |
| HELM | 多场景、多指标（准确率之外含校准、鲁棒性、公平性、效率等），并公开全部提示与输出 | 既有知识 | 多指标面板，公开原始运行记录，避免单一标量 |
| NetHack Challenge（NeurIPS 2021） | 符号规则智能体显著领先神经方法，表明结论依赖任务与算力约束 | 既有知识，需复核 | 按资源预算分赛道，避免不同量级混排 |
| Melting Pot Contest（NeurIPS 2023） | 评测使用训练时未见过的背景群体，检验泛化与协作而非记忆 | 既有知识，需复核 | 协作评测应引入未见伙伴与未见场景 |
| League of Robot Runners | 终身 MAPF 竞赛；强调严格的每步时间约束（约 1 秒）、大规模与拥堵 | 部分核对 | 评测须强制计算预算；需要规模梯度 |
| 公开测试集重测研究（如 CIFAR-10/ImageNet 重新采样测试集） | 长期公开测试集上的相对排名在新采样测试集上基本保持，但绝对分数下降 | 既有知识，需复核 | 相对排名尚可信，绝对数值不可作跨时间比较 |
| Papers with Code SOTA 表 | 众包 SOTA 表条件不统一（额外数据、预训练、测试时增强混排）；2025 年中站点关停 | 既有知识，需复核 | 条目带完整条件元数据；榜单不依赖单一商业站点 |

## 5. 协作智能排行榜的防坑规则

### 5.1 规则清单与 D4 处置

| 规则 | 内容 | D4 处置 |
|---|---|---|
| L1 | 三层数据：开发集（完整公开）、验证集（可见但限次）、私有测试集（仅服务端，隐藏场景与种子）；榜单分数只取私有测试集 | 采纳并扩为 `dev`/`validation`/`holdout`/`stress` 四划分；按地理区块、事件生成族与时间段隔离，平面世界按参数区块隔离 |
| L2 | 每方每赛季提交次数设上限；全部提交（含失败）可见；不允许撤回已入榜成绩；禁止多账号批量试探 | 采纳：`validation` 每团队每周 3 次、`holdout` 每月 1 次，只返回聚合统计；公开各团队获得的评测次数 |
| L3 | 私有场景定期轮换，历史私有集在赛季结束后公开并转入开发集 | 采纳：每半年部分轮换；赛季末公开盐与种子以验证承诺 |
| L4 | 评测在平台控制的容器内运行，无外网；Agent 拿不到世界真值 | 采纳并加固：分布式赛道每 Agent 独立沙箱、IPC 限流、GPU 共享策略、gVisor/runsc 评估 |
| L5 | 不使用单一标量；支配分层加置信区间，附协作增益、通信代价、计算代价面板 | 修改：每个 Suite 以主效用 `U` 排名（单 Suite 内单一主指标便于判定），资源–效用非支配分层为第二视图，Δ 族与资源为诊断面板；跨 Suite 不加权排序 |
| L6 | 名次附置信区间与排名稳定性；区间重叠者并列 | 修改：名次区间由重采样副本计算；并列采用"与组首比较"，判定依据为 Holm 校正后的"显著且实际更优"，而非区间重叠 |
| L7 | 重复次数由功效分析预先确定 | 采纳：取满足 `S·m/(1+(m−1)·ICC) ≥ 32` 的最小场景数 S，缺省 16 场景 × 5 种子 |
| L8 | 场景分层汇总，防止易场景主导；报告尾部表现 | 采纳：场景等权；报告失败率、10% 分位与 IQM（IQM 不单独使用） |
| L9 | 未见伙伴测试 | 暂缓：首发 Suite 以同一提交控制全队；未见伙伴（ad hoc teamwork）作为后续研究赛道候选 |
| L10 | 协作增益相对于"相同感知与算力、无协作"的平台版本化基线计算 | 采纳并细化为 Δ 族：`Δ_ind`（零通信同资源参考）、`Δ_cut`（阻断投递）、`Δ_perm`（载荷置换）、`R_central`（集中式参考差距），均在共同随机数下配对估计 |
| L11 | 协作分数与网络档绑定报告，不同档位不混排 | 采纳：网络档为赛道四元组字段之一 |
| L12 | 规模梯度 | 采纳：`n ∈ {4, 8, 16, 32, 64}` 恒密度缩放，报告饱和规模 |
| L13 | 算力分赛道 | 采纳：预算档 B1、B2、B-LLM，资源以 cgroup 实测计量 |
| L14 | 方法族标注 | 修改：方法族只作标签，不决定赛道（混合方法无法归类）；LLM 提交登记模型制品、采样参数与调用预算 |
| L15 | 可复现凭据：Run Manifest 与可回放 trace | 采纳：公开划分上可下载 trace 与 Run Manifest 并本地重放 |
| L16 | 内核或评分规则变化即新赛季 | 采纳：Board Version 冻结项与变更处置表 |
| L17 | 披露义务；按场景 ID 硬编码者取消资格 | 采纳：`submission.v2.declared` 必填；刚体盲化变换作为辅助 |
| L18 | 运营透明：评测调度规则、评测次数、变更日志 | 采纳 |
| L19 | 每赛季回顾是否鼓励无关方向的爬升，必要时调整或退役 | 采纳：赛季回顾为 P2 验收项 |
| L20 | 研究赛道接收负面结果与诊断报告 | 采纳 |

### 5.2 统计协议要点

| 项 | 规定 |
|---|---|
| 估计量 | 场景等权均值；场景内对外生种子与重复取均值 |
| 统计单位 | 场景配置；同场景不同种子不是完全独立样本 |
| 估计目标 | Suite 声明：`family`（场景由生成器随机抽取，推断生成分布上的均值）或 `fixed_set`（固定设计集合，结论不外推） |
| 区间 | `family` 只在场景层有放回重采样并以 bootstrap-t 构造区间；`fixed_set` 只在场景内重采样种子；不做两层同时重采样（会重复计入场景内方差）；`n_boot = max(10,000, ⌈20·m_fam/α⌉)` |
| 配对 | 同一（Board Version, 赛道, 场景集）内全部条目共用同一组重采样下标，随机数由公开可复算的 `SHA-256("drone4d.board.resample.v1" ‖ board_version ‖ track ‖ scenario_set)` 派生，不含条目 id，不使用服务端密钥 |
| 多重比较 | 检验族限定为"与组首""与独立参考"两类比较（并列与判定词）及支配分层的单方向无序对，分别施加 Holm 校正；单侧检验 `H0: μ_A − μ_B ≤ 0`；p 值取 `(b + 1)/(B + 1)` |
| 判定词 | "显著且实际更优"要求 Holm 拒绝且点估计差 > ε（ε = 0.02，保证关系无环）；"等价"要求差值 90% CI 落入 `[−ε_eq, ε_eq]`（`ε_eq = 0.05`）；其余为"未判定" |
| 样本量 | 按实际单侧检验与 Holm 步阈值推导：`n_eff* = ((z_{1−α′} + z_{0.8}) σ_D / δ)²`，规划阈值 α′ = 0.01、`σ_D = 0.10`、`δ = 0.05` 时约 40.1；以配对差的设计效应 `1 + (m − 1)·ICC` 修正，ICC 取 pilot 估计的置信上界；ICC = 0.3、m = 5 时需 18 个场景（详见概念设计 §8.6） |
| 失败计分 | 策略原因失败该 Episode `U = 0`；基础设施故障原样重跑一次；无效运行缺省记 0，不剔除；任一场景有效种子少于 3 个则条目不完整 |
| 学习型方法 | 训练种子为额外方差来源，正式报告要求多个独立训练产物 |
| LLM 方法 | 固定模型制品、声明采样参数、每（场景, 种子）至少 3 次重复、响应缓存回放 |

### 5.3 防作弊威胁与控制

| 编号 | 威胁 | 控制措施 |
|---|---|---|
| A-01 | 读取世界真值 | 观测白名单信封；真值层物理分文件；不提供免费的"是否完成"查询；运行末泄露审计 |
| A-02 | 跨 Agent 旁路通信 | 每 Agent 独立沙箱、仅私有 IPC；无出站网络、只读根文件系统；禁共享可写挂载与宿主 `/proc`；高风险提交用 microVM |
| A-03 | 预算绕过 | 同容器多 Assignment 之间的数据交换同样经网络服务计费；LLM 内部对话计入团队通信预算 |
| A-04 | 资源超用 | cgroup 实测 CPU（含全部线程）、GPU 时间与 token 进入资源账本，超额按违规处置 |
| A-05 | 隐藏集探测 | 提交配额、聚合反馈、身份核验、全部提交可见、入榜不可撤回；监测"分数与提交次数相关" |
| A-06 | 择优发布 | 每团队每赛道只取最近完成的代表提交；公开变体数量与评测次数 |
| A-07 | 场景识别与硬编码 | 地理隔离留出集为核心；一致的刚体盲化变换为辅助 |
| A-08 | 时序侧信道 | 墙钟不进入成绩 |
| A-09 | 运动隐写 | 对队友位姿观测加标准化噪声并低通；审计异常高频动作 |
| A-10 | 评测器博弈 | 报告速率限制；主排名只用 `U`；置换干预的"过敏反应"审计 |
| A-11 | 供应链 | 镜像摘要、SBOM、依赖许可证、模型哈希；前列提交静态审计与重放 |
| A-12 | 披露缺失 | 声明外部数据、预训练、人工调参、场景特化逻辑与方法族标签 |

否决的措施：向正式传感器注入金丝雀伪目标（污染基准且检测不到内存扫描）；同容器多 Agent 上下文作为隔离；随机切分瓦片作为划分方式。

### 5.4 版本化与结果复核

- **Board Version 冻结项**：Suite 摘要、赛道集合、场景集摘要、实例集承诺、种子集承诺、评分版本、评测器主版本、内核版本、平台摘要。评测器缺陷修复且不改变已存储分量为补丁版本，指标或实例集变化为新 Board Version，内核语义变化（黄金 trace 摘要改变）为新赛季。
- **种子承诺**：`seed_set_commit = SHA-256(salt ‖ JCS(sorted(seeds)))`，盐与种子只存于服务端，赛季末公开以供验证；承诺对象是真实种子值而非序号；`rows.jsonl` 每行另写入 `seed_tag = HMAC-SHA256(salt, episode_id ‖ scenario_id ‖ seed_index ‖ ω)` 与真值层摘要，把分数与已承诺的种子逐行绑定。
- **结果复核**（条目由 `provisional` 升为 `verified`）：新种子复跑落入原区间或差值 < ε；同一硬件等级的第二台机器上位级复现、不同硬件等级上统计复现；静态与行为审计；由私有 trace 离线重算全部分量并逐位一致。
- **平台审计**：每日以参考策略复跑抽样 Episode 并比对摘要，不一致即冻结该 Board Version 的新评测。

## 6. D3 现有评测设施的评估

D3 已具备容器化提交、提交状态机、两阶段自助法置信区间、统计并列、支配分层榜 `board.v1`、团队代表条目与榜单版本冻结；评测与榜单代码中约 55%–60% 与具体任务语义无关，可参数化复用。本轮核对发现的方法学偏差如下（均登记于 D3 封板清单，不追溯修改已发布的 `board.v1`）：

| 编号 | 偏差 | D4 处置 |
|---|---|---|
| D-1 | 重采样随机数以 `sha256` 派生（设计文档写为 HMAC），种子承诺以行内序号计算 | 重采样以公开的域分隔 SHA-256 派生且不含条目 id（以代码现状为准）；对真实种子值做加盐承诺并逐行绑定 |
| D-2 | 无效运行：设计文档为"记 0、不剔除"，代码为"只按有效运行计算，占比超阈值则整条无效" | 缺省 `invalid_policy = zero` |
| D-3 | 设计文档规定展开为"全部事件 × 种子 × 重复"，代码只循环种子 | 展开为"场景集 × 种子 × 重复 × 干预" |
| D-4 | 容器加固参数与设计文档不一致 | 统一到赛道预算档与运行策略 |
| D-5 | 配额为常量 | 配额策略对象 |
| D-6 | "成对差值区间"并非配对：每个条目使用独立重采样下标 | 重采样下标按（Board Version, 赛道, 场景集）共享 |
| D-7 | 正式成绩只允许高保真锁步物理档 | 该规则限定于 D3 任务；D4 各 Suite 声明合格物理档并以跨保真度判据约束外推 |
