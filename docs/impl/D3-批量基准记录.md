## 1. 范围判定

1. D3-AC-42 原文（§11）："无人值守完成 ≥ 100 次运行，自动评分并导出标准化数据集（MCAP、LeRobot、OpenLABEL、bag、`.rrd`）；失败运行自动重试且最终失败率 ≤ 2%；运行期间存储占用与写带宽不超过 ADR-163 的预算"，验证工具 `tools/bench/d3/batch_matrix.py`，环境"独占 A40 + dmax CPU 池"。
2. ADR-194 决策 (2) 把 P1 至 P3 的 27 条验收移出 D3 封板，其中阻塞项含 D3-AC-42；§23.3 推荐去向为"D4 候选（AWR-06 Benchmark Suite）"。顺延不是豁免：编号与阈值原样保留，交付时按原阈值验收，不计入 D3 封板分母。
3. ADR-195 决策 (4) 的窗口排期写明"原计划的 B33 窗口随 P3 移出取消"；封板计划中的前置任务 B31（`batch_matrix.py` 无人值守批量驱动）与 B32（LeRobot 导出与统一导出 CLI）不在封板任务表，`awr.bench.export.dataset` 对 `lerobot`、`openlabel` 两种格式返回 689 `format_unavailable`（`DEFERRED_FORMATS`，注明 ADR-194 移出）。
4. 因此本任务不新建 P3 工具、不占用独占窗口重跑 100 次批量，而是：(a) 以已完成的 130 个 gz 锁步 Run（B10 第 2 轮，无人值守、含评分与内部提交）为批量样本，测量 D3-AC-22 在批量规模下的存储、写速率与 MCAP 阻塞（D3-AC-22 属 P0b，在封板范围内）；(b) 在 dmax 真实 L2 运行的副本上执行生产路径 `finalize_ranked_eval`，处理 §29.5 F-67 中"在 dmax 含 LiDAR 的运行上执行一次 `compact_ranked` 复验 D3-AC-22"一项；(c) 对 D3-AC-42 逐条登记现有证据与差距，供 D3.x 或 D4 交付时复用（§3）。
5. 独占口径：本记录不产生性能类正式数字。存储体积、写入字节与 MCAP 阻塞比例由 B10 第 2 轮的运行产物与清单得出；该轮在共享卡上执行（ADR-194 决策 (7) 的"原型"），写速率为按 Run 起止时刻重建的估计（§4.2）。D3-AC-22 写速率与 MCAP 阻塞的正式数字仍以 S21（A 级独占，2026-10-19）为准，本记录作为批量规模的补充证据。

### 2.2 工具

审计与精简工具为本任务的取证脚本 `b33_storage.py`（随记录归档在 `results-B09a/B33-artifacts/`，含合成数据自检 `test_b33_storage.py`；不进入仓库，D3-AC-42 的正式工具 `batch_matrix.py` 随 P3 顺延）：

- `audit`：逐 Run 统计目录内各项字节（`raw.mcap`、`frames.idx`、`truth/`、`agents/` 等）、计时（`run_manifest.json` 的 `timing`）、尝试次数与无效原因；以 `retention.compact_ranked(dry_run=True)` 求精简后保留体积（只计划不删除，不写入审计）；按 Run 起止时刻把字节均匀摊到 1 s 分桶，取 60 s、10 s 与 600 s 滑动窗口（步长 10 s、1 s、10 s）的写速率分位数。
- `compact`：把选定 Run 复制到独立数据根 `b33/work/dataset/crop-handoff-001/runs/`（跳过运行目录残留的 gz 控制套接字），以生产入口 `retention.finalize_ranked_eval` 执行抽样、精简与去重（抽样随机源固定为 `random.Random(33)`，生产缺省为 CSPRNG），然后以"抽样到期前 1 天"与"到期后 1 s"两个时刻干跑 `retention_gc`，核对抽样录制的到期精简。

第一次 `audit` 以 8 个进程同时计算全部 130 个 Run 的逐帧摘要（`frames_digest` 读取全部 `raw.mcap`），与同时段运行的 B21 正式评测争用 `/data` 盘（系统 I/O 压力 full avg60 约 25%），在完成 60 个 L1 与约 16 个 L2 后中止，改为只读文件元数据的体积审计（不读 `raw.mcap`，单次 0.02 s/Run），并对精简实验的容器加块设备限速。逐帧摘要的读放大见 §5 第 4 项。

### 2.3 MCAP 阻塞与丢帧

逐 Run 清单 `manifest.json` 的 `recorder.writer_block_frac` 与 `recorder.dropped`（B23、S21 同口径：MCAP 阻塞 = 逐 Run `writer_block_frac` 的最大值）。

对照：

- §5.6.4 "720p 参考配置每次运行（3 机 × 360 s）持久数据约 6.5–7.3 GB（`raw.mcap` 约 5.5–6.2 GB，真值约 0.9–1.1 GB）"：实测 L2 `raw.mcap` 5.65–5.82 GB 在区间内；`truth/`（位姿、可见度行、接触、运行种子与运行真值 MCAP）中位 27.9 MB，远低于估计的 0.9–1.1 GB，真值层构成与估计条件的差异待体积口径复核（§5 第 6 项）。

- `/data/d3` 配额 10 TB（M27-FR-060，80% 告警、95% 停止准入）：本批全量保留占 4.04%；按 ADR-163 v1.3 精简后（§4.4）每 L2 Run 约 26 MB，130 个 Run 合计约 2.6 GB 加抽样完整录制。
- §5.6.4"评测运行每 Run 持久约 0.1 GB 加抽样完整录制"：精简后 L2 每 Run 25–27 MB，L1 约 20 MB，均低于 0.1 GB。
- L1 每 Run 31.7 MB，高于 §5.6.4 引用的 r6 值"L1 `raw.mcap` 439 KB"：本轮 L1 `raw.mcap` 中位 6.70 MB，`truth/` 20.0 MB；体积口径表应补 L1 实测行（§5 第 6 项）。

## 5. 发现与后续

1. **评测运行未接入精简（影响 D3-AC-22 保留条款）**：`retention.finalize_ranked_eval` 只被 `tools/bench/d3/write_load.py`（B23 负载工具）调用；`mbl_e2e.py`（B10 正式口径）、`subworker.py`（内部与受邀提交的正式评测）与 B21 的排行榜正式评测在评分后都不调用精简，B10 第 2 轮的 130 个排名运行与提交运行全部以全量录制保留（404.4 GB）。D3-AC-22 原文"`ranked_eval` Run 在评分后只保留逐帧摘要与 `truth_min`"在库层面通过（§4.4），在生产路径上尚未生效。建议在 RP0b 前由提交链路的负责任务在"评分完成"后调用 `finalize_ranked_eval`（提交：`subworker` 的评分步骤之后；参考基线与正式口径：`mbl_e2e` 的 board 阶段之后），并对已存在的 B10、B21 产物执行一次补登记与精简（被排行榜引用的 Run 先以 `sync_references` 升为 pinned）。
2. **重复运行去重对 LiDAR 运行不生效（D3-AC-22）**：`lidar_frame.v2` 帧头的 `frame_id` 为 `<run_id>/<uav>/<sensor>/<seq>`，同一帧流的两次重复存档字节不同（§4.4）。建议二选一：(a) 录制端 `frame_id` 不含 run_id（例如 `<uav>/<sensor>/<seq>`，run_id 已在 MCAP 元数据中）；(b) `frames_digest` 对 LiDAR 载荷以去掉 `frame_id` 的规范化字节求哈希并在摘要版本中注明。修复后以 B10 的 60 对重复复核去重。
3. **精简后不能逐字节重算 `evaluation.json`（D3-AC-22 与 D3-AC-18、57 的交汇）**：`inputs.truth_sha256` 覆盖 `truth/run_<id>.mcap`，精简后该文件被删除（§4.4）。建议二选一：(a) 把 `truth/run_<id>.mcap`（每 L2 Run 约 6.9 MB）加入 `TRUTH_MIN_FILES`；(b) 评测器的 `truth_sha256` 只覆盖实际读取的真值文件（`l1.jsonl`、`l2.jsonl`、`fleet.npz`、`contacts.jsonl`），评测器升版本并在 M27 说明。同时修订 ADR-163 v1.3 与 M27-FR-171 中 `truth_min` 的证据帧条款：Env 运行不录 `camera_gt`，`truth_min.evidence` 为空，应写明证据帧的真值来源（可见度行 `l2.jsonl` 的 `bbox_xywh`）或改为录制证据帧实例图。
4. **逐帧摘要的读放大**：`frames_digest` 经 `FrameStore.index_page` 按通道逐帧取消息，块缓存在通道之间反复解压同一 MCAP 块。第一次审计中 8 个进程约 50 min 完成 60 个 L1 与约 16 个 L2 的摘要，另有 8 个 L2 在途，容器累计读盘约 654 GB，约为这些 Run 数据体积（约 130 GB）的 5 倍；精简实验中每个 L2 Run 的 `finalize_ranked_eval` 约 569 s。按 B21 每窗口 400 个 Run 计，评分后精简约需 63 h 单进程时间。建议按文件顺序单遍扫描 `raw.mcap`，或在录制时把交付帧的 sha256 写入 `frames.idx`，精简时直接读索引。
5. **运行目录残留 gz 控制套接字**：提交 Run 的 `phys/sock/ctl.sock` 在运行结束后仍留在运行目录（套接字文件，不占体积）；`shutil.copytree` 与部分备份工具遇到套接字会报错。建议 Run 收尾时删除 `phys/sock/`。
6. **体积口径表补实测行**：§5.6.4 引用的"L1 3 机 360 s 的 `raw.mcap` 为 439 KB（r6）"与本轮实测 6.70 MB 不符（另有 `truth/` 20.0 MB）；720p 参考配置的"真值约 0.9–1.1 GB"与本轮 L2 `truth/` 27.9 MB 不符。建议在 §5.6.4 体积口径中补 B10 第 2 轮的 L1、L2 实测行并注明通道与真值层构成。
7. **提交 Run 的清单不含计时与尝试次数**：`benchroot/dataset/*/runs/sub-*` 只有 Env 的 `manifest.json`（含 `wall_s`），没有 `run_manifest.json` 的 `timing.started_unix_ns`、`ended_unix_ns` 与 `attempt`；批量统计须另读提交记录。D3-AC-42 的批量驱动应统一逐 Run 清单字段。
8. **D3-AC-42 顺延事项**：按 §3 的差距列登记到 D3.x 或 D4（AWR-06 Benchmark Suite）：`batch_matrix.py`、LeRobot 与 OpenLABEL 数据集导出、统一导出 CLI、独占窗口的 ≥ 100 次批量、故障注入下的重试统计。
