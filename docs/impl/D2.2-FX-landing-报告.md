## 1. 逐条复核结论

### 1.1 [major，已修复] 滚动揭示动画可能让正文内容（含实景截图）保持不可见

- 根因：`apps/web/src/app/demo/Landing.tsx` 的 `useReveal()` 只在挂载时做一次性检查（已在视口内的元素直接揭示，其余交给单次 `IntersectionObserver`），没有任何超时或滚动兜底。复核报告描述的"400px/60ms 连续滚到底、停留 1200ms 仍有 4/33 未揭示"场景下，部分元素可能恰好落在两次 IntersectionObserver 采样之间、从未被判定为"相交"，就永久停留在 `opacity:0`。
- 修复：`useReveal()` 保留 IntersectionObserver 作为主路径，同时加一个确定性兜底——`scroll`/`resize` 事件（经 `requestAnimationFrame` 节流）与一个 400ms 的 `setInterval` 共同驱动一次"扫描"：凡是视口已经到达或越过的元素（`top < innerHeight`），或者已经滚到页面底部时剩下的全部元素，一律立即揭示；全部揭示后自动停止监听与计时器（不留常驻定时器）。
- 复核方法：先用**未修复**的旧实现跑新增用例（见 1.1 回归用例），复现"33 个 `.landing-reveal` 中只有 14 个揭示"；换回修复后的实现，同一用例变为 33/33。确认用例确实在验证这个缺陷。
- 回归用例：`apps/web/perf/d22/landing.spec.ts`「reveal: a fast scroll to the bottom (400 px every 60 ms, no backtrack) reveals every section (D2.2-R-landing §2.1)」，并在既有「reduced motion」用例里追加"无常驻动画"断言（见 1.5）。

### 1.2 [major，已修复]"开启我的沙盒"场景模板在英文界面下仍强制显示中文

- 根因：`apps/web/src/ui/sandbox/StartSheet.tsx` 的 `templateLabel()`/`TemplateLines()` 无条件优先用服务端的 `name_zh`/`summary_zh`/`first_feedback_zh`，不判断当前界面语言；即使退回 i18n key，`en.json` 里 `sandbox.template.*`（t1–t6 的名称/简称/首次反馈）、`sandbox.limitedBy.*`、`sandbox.endReason.*`、`sandbox.band.*` 共 33 个键是空字符串，回退规则会再退回中文。
- 修复：
  1. `StartSheet.tsx`：`templateLabel`/`TemplateLines` 改为只在 `getLocale() === 'zh-CN'` 时才使用服务端的 `zh_` 字段，英文 UI 一律走 i18n 字典（服务端目前没有 `name_en` 等字段，前端据此选择，不是等后端补充）。
  2. `apps/web/src/app/i18n/en.json`：补全上述 4 个前缀下共 33 个空字符串键的英文译文（一次性脚本读取 JSON、只改这 33 个键、立即写回；修改后用 `python3 -c "import json;json.load(...)"` 校验 JSON 合法，`git diff` 核对只改了这 33 行）。
- 回归用例：`apps/web/tests/m15/startSheetLocale.test.ts`（Vitest unit，Node 环境，`renderToStaticMarkup` 渲染 `TemplateLines`）：zh-CN 下使用服务端 `zh_` 字段、en 下绝不渲染服务端中文字段并落到 i18n 字典；另有 `en.json` 该 4 个前缀"无空字符串"与"t1–t6 齐全"的断言。

### 1.3 [major，已修复] 落地页 JS 入口分块里大部分字节是未裁剪的全量中英文 i18n 词典

- 根因：`apps/web/src/app/i18n/index.ts` 在模块顶层无条件 `import` 完整的 `zh-CN.json`（2581 键）、`en.json`（同量级）与 `reasons.zh-CN.gen.json`，`vite.config.ts` 的 `LANDING_MODULES` 又把整个 `app/i18n/` 目录强制并入落地页的 `landing` 物理分块；落地页本身（`Landing.tsx`/`LandingHeader.tsx`/`LandingSections.tsx`）只用到 `landing.*` 前缀下几十个键，外加它自己的容量行用到的 `capacity.*` 若干键。
- 修复（仿照仓库里已有的同类先例 `virtual:awr-boot-i18n`／`bootI18nPlugin`，而不是另造一套机制）：
  1. 新增 `apps/web/src/app/demo/landingKeys.ts`：落地页真正用到的 i18n 键的显式清单（`landing.*` 静态键 + `LandingContent.ts` 的能力/媒体/技术栈/路线图 id 派生出的动态键 + `capacity.*`），共 131 个。
  2. `vite.config.ts` 新增 `landingI18nPlugin`/`virtual:awr-landing-i18n`：构建期按这份清单从同一份 `zh-CN.json`/`en.json` 筛出两份小词典（缺键直接抛错，不会悄悄塞空字符串），`LANDING_MODULES` 不再整目录捕获 `app/i18n/`，改成只认这个虚拟模块。
  3. 新增 `apps/web/src/app/demo/LandingI18n.ts`：落地页自用的最小 i18n 运行时（`t`/`useT`/`setLocale`/`getLocale`，接口与共享版一致），读这份虚拟模块而不是共享的 `@/app/i18n`；容量文案复用 `app/boot/capacityText.ts` 的纯函数（不经过会带上完整词典的 `app/i18n/capacity.ts`）。
  4. `Landing.tsx`/`LandingHeader.tsx`/`LandingSections.tsx` 改为从 `./LandingI18n` 取 `t`/`useT`；`Landing.tsx` 的 `openSheet()` 在懒加载"开启我的沙盒" Sheet 之前，先动态 `import('@/app/i18n')` 把共享 locale 同步成落地页当前选的语言，保证 Sheet 与应用后续界面语言一致。
  5. `entry.tsx`：原来在模块顶层无条件 `import { t } from '@/app/i18n'`（供应用路由的启动进度条/版本号复制用），即便访问的是落地页也会把该模块拉进图里；改为只在应用路由分支里动态 `import('@/app/i18n')` 再用其中的 `t`。
- 效果（用复核报告的同一方法复核）：`landing-*.js` 从 478,187 B（gzip 150.66 KB）降到 283,843 B（gzip 83.30 KB）；对新分块做字符串统计，不再包含任何"落地页从不读"的键（如 `fleet.count`、`sandbox.endReason.failed`）。复核报告"约 92%/441,932 字符"的统计用的是宽松的类 JSON 文本匹配，实际两份完整词典的原始字节合计约 231 KB；修复后分块仍含约 266 KB 的 Base UI/shadcn 组件运行时、图标注册表与品牌资源代码——这些是落地页本来就要用的依赖，不是未裁剪词典，不在本条修复范围内。
- 回归用例：
  - `apps/web/tests/m15/landingDict.test.ts`：虚拟模块的筛选函数行为正确、缺键即抛错；并从 `LandingContent.ts` 真实的能力/媒体/技术栈/路线图 id 反向核对 `landingKeys.ts` 没有漏改（防止以后新增一个能力卡片却忘了把它的键加进清单，导致该键静默回退成 key 名/中文）。
  - `apps/web/perf/d22/landing.spec.ts`「first screen: the landing chunk carries its own trimmed dictionary...」：实际构建产物里抓落地页分块，断言不含已知的"仅应用才用"的键、总字节远低于旧词典体量。

### 1.4 [minor，不成立] 全站强制深色，没有随系统浅色偏好或手动切换的路径

- 核实：这是已有设计基线的既定决定，不是缺陷或遗漏。`docs/15-视觉设计规范与色卡.md` 第 141 行明确写着："暗色是默认（`<html class="dark">`），浅色只在报告路由与导出中启用（Q7）。D1 的产品 UI 不提供浅色切换入口；设置页的主题项留待 V0.2 视报告预览需求再定。"（依据 ADR-032、Q7，VIS-FR-002）。落地页作为产品 UI 的一部分，沿用同一条策略；浅色主题目前只服务于报告/导出路由，不适用于落地页。
- 结论：维持现状，未改代码。复核报告建议"若是既定设计,在设计基线文档中写明"——已经写明，只是复核时未检索到该文档的这一条，故此处把出处列清楚，供后续复核直接引用，不必再重复提出。

### 1.5 [minor，已缓解] Showcase 画廊懒加载图片偶发出现空白占位

- 核实：复核报告自己的描述是"间歇性，定向复现同一张图时该图正常加载完成"——不是资源 404 或损坏，更像是原生 `loading="lazy"` 在快速/程序化滚动下的时序问题，不是每次必现，本次也未能稳定复现该现象本身。
- 修复（在能确认有效的范围内）：
  1. `<img>` 增加 `onError` 兜底：失败时带 `?retry=1` 重试一次，仍失败则落到浏览器自身的"图片损坏"呈现（`alt` 文字始终可读）。
  2. 增加 `data-media-loaded` 状态（`onLoad` 置位），让"是否已加载完成"从视觉上的灰色方块变成可编程检查的显式状态，便于后续排查与测试。
  3. 原计划再加一个 `animate-pulse`"骨架屏"呼吸效果（参考 `ui/components/ui/skeleton.tsx` 的 `animate-pulse + bg-muted` 语言），`make lint` 的 `motion-lint`（MOT-03，ADR-029）跑出来才发现：全应用"常驻无限循环动画"预算是 2，`styles/motion/recipes.css` 的 `ShimmerText`/`MatrixLoader` 已经用满，加第三个会让 lint 失败。因此放弃常驻动画，保留静态的 `bg-muted` 占位块 + 上述两项改动。
- 结论：失败兜底与状态可见性已落实；"加载中呼吸骨架屏"这部分因全局动画预算已满而未采用，图片仍是静态灰色占位块（视觉上与修复前一致，只是现在有了失败重试与可测的加载状态）。
- 回归用例：`apps/web/perf/d22/landing.spec.ts`「showcase: every lazy image reaches data-media-loaded=true, none stuck pending」。

### 1.6 [minor，不成立] iPad Pro 11 横屏（1194px）顶部导航已收进汉堡菜单

- 核实：复核报告自己已把这条定性为"文档化的既定行为而非缺陷"（`Landing.tsx` 文件头注释明确写了 1280px 断点），只是建议产品侧确认这个阈值在大尺寸横屏平板/笔记本场景下是否合适。这是一个产品决策问题，不是代码缺陷，本任务未改代码。
