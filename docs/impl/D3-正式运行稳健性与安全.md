## 2 GPU 丢失（B21 遗留 3；D3-AC-57 (d)）

### 2.1 故障机理与复现

B21 记录：2026-10-22T07:08:12Z 宿主执行 systemd reload 后，运行中容器的设备 cgroup 规则被重置。容器内 `/dev/nvidia*` 节点仍在，但 `open()` 返回 EPERM。此后新建的进程中，Warp 初始化报 `Warp CUDA error 100: no CUDA-capable device is detected`，并静默退到 Warp CPU 设备；随后 EGL 渲染器建上下文时段错误，导致评测进程（`sub-relay-l2`）或进程池（`base-l2`，其余 Run 全部 `BrokenProcessPool`）崩溃。跨过 reload 时刻、上下文已建立的 Run（`k4r0`）正常完成，因此体检放在每个 Run 建立 GPU 上下文之前，而不是逐 tick 检查。

dmax 复现（不使用 GPU 计算）：以 d3-sensorsvc:dev 启动容器，只读挂载宿主 NVIDIA 驱动库与 `10_nvidia.json`，并以普通绑定挂载（不经设备 cgroup 放行）提供 `/dev/nvidiactl`、`/dev/nvidia2`、`/dev/nvidia-uvm`，设 `NVIDIA_VISIBLE_DEVICES=2`。结果如下：

- 三个节点 open 均为 EPERM；
- Warp 1.17.0 报出与 B21 相同的 `CUDA error 100 (init_cuda_driver)`，CUDA 设备数为 0；
- EGL 上下文落到 Mesa llvmpipe 软件渲染（没有段错误，但帧已不来自 GPU）；
- `require_gpu` 与 `L2Sensors(...)` 均抛 647 `SENSOR_GPU_UNAVAILABLE`（`cause = gpu_lost`、`platform_failure = true`）。

### 2.2 实现（`awr.sensorsvc.gpuhealth`）

| 机制 | 说明 |
|---|---|
| 是否应有 GPU（`gpu_expected`） | 存在 NVIDIA 设备节点、`NVIDIA_VISIBLE_DEVICES` 指定了设备（不为空、`void`、`none`），或 `AWR_REQUIRE_GPU=1`；无 GPU 的开发机与纯 CPU 容器不体检，行为不变 |
| 设备节点（`check_device_nodes`） | 逐个只读打开 `nvidiactl`、`nvidia<N>`、`nvidia-uvm`（只 open/close，不发 ioctl）；EPERM、EACCES、ENXIO、ENODEV、EIO 判丢失 |
| EGL（`probe_egl`） | 在独立解释器中按 `RasterCamera` 的同一调用建立并释放 EGL 上下文；子进程被信号终止、失败或落到软件渲染（llvmpipe、softpipe、Mesa）判丢失，父进程不受驱动崩溃影响 |
| Warp | 应有 GPU 而 Warp 看不到 CUDA 设备即判丢失；`open_mesh_lidar(backend="warp")` 不再静默退到 Warp CPU 设备 |
| 体检档位（`AWR_GPU_PROBE`） | `full`（缺省：设备节点 + EGL 子进程，约 1 至 2 s/Run）、`nodes`（只查设备节点）、`off` |
| 运行中（`gpu_errors`） | Env 的 L2 建立、每 tick 感知与真值归约，以及 LiDAR 工作进程回报，凡消息带 CUDA 100 / 999、NVML、EGL 初始化失败特征，或异常发生时设备节点已打不开，均转为 647；其余异常原样抛出 |

接入点：`L2Sensors.__init__`（缺省 EGL 渲染器或进程内 Warp LiDAR 时，在构造之前体检，记录写入运行清单 `l2.gpu_probe`）、`BenchEnv.reset`、`BenchEnv._sense`、`BenchEnv._flush_truth`、`_LidarProc._get`、`warp_mesh.open_mesh_lidar`。647 在 contracts `rt/reasons.json` 中已登记（HTTP 503，remedy"排队"）。subworker 与 `board_v1_formal.py` 以异常判平台失败并重跑一次，不计入提交方。

### 2.3 正式窗口的宿主侧建议（待运维确认）

体检只能把崩溃变为可重跑的平台失败；GPU 未恢复前，重跑仍以 647 失败。正式窗口须从宿主侧消除诱因：

1. **主机变更冻结**：正式评测窗口（含 Worker 与 subworker 运行期间）内不执行 `systemctl daemon-reload`、软件包安装或升级（含 `unattended-upgrades`，其安装后脚本常触发 reload）、Docker 或 containerd 重启、NVIDIA 驱动与 Container Toolkit 变更。窗口开始前登记、结束后解除；dmax 为共享生产机，冻结须与其他项目协调。
2. **CDI 设备注入**：以 CDI 声明 GPU 设备（`docker run --device nvidia.com/gpu=2`），设备节点与 cgroup 规则写入容器的 OCI 规格，由 runc 经 systemd 配置，systemd reload 后不会被重置；旧的 `--gpus` 方式由 hook 在 systemd 不知情时修改 cgroup，reload 后即丢失。dmax 现状：NVIDIA Container Toolkit 1.18.1，CDI 规格 `/var/run/cdi/nvidia.yaml` 已生成，Docker 29.1.4。本任务执行环境为 CPU，未在 GPU 上实测 CDI 注入；改用前须在独占卡上验证 EGL、Warp、nvJPEG 三条路径与正式运行的逐字节一致。改用后 `run_subworker.sh`、Worker 与测试入口中的 `--gpus device=N` 一并替换。
3. **恢复**：已失去设备访问的容器不可恢复，须重建容器；恢复后先在该卡上运行体检（`python -c "from awr.sensorsvc.gpuhealth import require_gpu; print(require_gpu(warp=True))"`），通过后再恢复领取。

## 3 撞机发散守卫（B21 遗留 5）

`awr.phys.gz.backend.GzSimBackend` 在样本块写入 PoseHistory 与样本流摘要之前，逐机逐步检查以下条件：

| 判据 | 阈值 | 适用 |
|---|---|---|
| 状态含非有限值 | — | 全部机体 |
| 速度 | > 100 m/s（`GUARD_V_MPS`；x500 平飞上限约 20 m/s，150 m 自由落体约 54 m/s） | 全部机体 |
| 角速度 | > 1000 rad/s（`GUARD_OMEGA_RPS`） | 全部机体 |
| 位置分量绝对值 | > 1e5 m（`GUARD_POS_M`，与 B21 发散扫描同一阈值） | 全部机体 |
| 离坠毁点位移 | > 500 m（`GUARD_DRIFT_M`） | 已坠毁机体 |

- 触发后，该机体自触发步起冻结为最后一个合理样本：位置、姿态与比力保持，速度与角速度置零。此后各 tick 的样本均为冻结值，Env、录制（`raw.mcap` 真值层、`fleet.npz`）与 L2 渲染只见有界值。
- 已坠毁机体只冻结。未坠毁机体发散时按坠毁处理：`crash = impact`，给出一条 IMPACT 接触，Env 以 CRASHED 终止该机。
- 守卫只取决于样本值，重放（`SupervisedGzBackend` 的逐 tick 摘要比对）逐位一致。触发记录写入 `close()` 的 `crash_guard`，即运行清单的 `tier_info.crash_guard`，字段为 `uav`、`t_ns`、`reason`、`crashed_before`。
- 未发散的运行样本块原样写入，样本流摘要与 K18 之前相同，既有确定性基准不受影响。
- 守卫在宿主侧，gz 内的发散机体仍继续积分，但其状态不再进入平台数据。若需在 gz 内移除坠毁机体，归 D3.x（§7）。

## 5 L2 世界查询缓存路径（B21 遗留 9）

`awr.agentsdk.env.l2.worldquery_cache_dir(world_dir, explicit)` 的取值顺序如下：

1. `explicit`，即 `L2Config.cache_dir`，或 `BenchEnv(l2_cache_dir=...)` 传入的值；
2. 环境变量 `AWR_WORLDQUERY_CACHE_DIR`（非空时）；
3. 按部署布局推导 `<worlds 的上级>/cache/worldquery`。dmax 的 `$D/worlds` 与 `$D/cache/worldquery` 沿用此路径，保留为缺省，避免已有缓存失效。

L2 LiDAR 工作进程、进程内扫描与 `awr.phys.tier_compare` 共用该函数。缓存只影响装载耗时，不进入运行哈希与观测字节。

## 7 遗留

1. **subworker 对 647 的处置（K17 范围）**：当前平台失败即刻重跑一次，GPU 未恢复时第二次仍以 647 失败，导致提交 FAILED。建议对 `cause = gpu_lost` 暂停领取并告警，待设备恢复后续跑，不消耗重跑次数。
2. **runner 与 subworker 传入 `seed_sink`**：数据集布局已自动写入隐藏区。`awr.bench.runner.run_job` 若需显式指定隐藏区（例如数据根之外的 EvalStore 目录），可经 `EnvSpec.from_run_spec(..., seed_sink=...)` 传入。
3. **CDI 实测**：在独占卡上验证 CDI 注入下 EGL、Warp、nvJPEG 与正式运行的逐字节一致，之后替换各入口的 `--gpus`（§2.3）。
