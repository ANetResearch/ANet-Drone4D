## 3. D3-AC-34 Realistic 档锁步的性能条款

### 3.1 测量

- 工具：`tools/bench/d3/gz_lockstep.py run --repeats 3 --m25-runs 1`（P03 交付）：3 架 x500（`p600_bench` 质量与惯量映射）由 BenchEnv 驱动 360 s，物理档为每 Run 新起的 gz `physics` 兄弟容器（`d3-gz:dev`，`--cpus 2 --memory 2g`，不挂 GPU，无网络），资源由宿主 cgroup v2 每 1 s 采样。
- 口径：ADR-195 决策 (6) 规定 gz `physics` 实例的 RTF 与资源在 CPU 池测量，前置条件为 `d3.slice` 内无其他 D3 批作业。`physics` 类运行（L1，无 M25 负载）不使用 GPU，其 RTF 与启动时长与 GPU 独占级别无关；`m25` 类运行（L2 + M25 会话）使用 GPU 2，只用于"有无 M25 负载时物理轨迹逐位一致"等非性能条款。两组 `physics` 运行期间 dmax 上除常驻服务容器（registry、lab 等）外无其他 D3 批作业容器，`/data/anet-drone4d-d3/d3dev` 下除本任务外无目录变动，宿主 loadavg 5.9–11.8（64 线程）。

  - 第 1 组（`out/gz`，18:56–19:25）：guard 持主机排他锁，窗口前 600 s 外部进程只驻留（B 级候选），窗口内外部推理服务恢复计算（536 个活动采样），guard 判 invalid。`physics` × 3 不受影响；`m25` × 1 的 GPU 部分为共享卡。

## 4. D3-AC-22 1 h 写速率与 MCAP 阻塞

### 4.1 测量

### 5.3 分析

- 与共享卡参考相比，独占卡带来 10–25% 的提升，但与阈值的差距仍为 1.8–4.5 倍：

## 8. 遗留与待确认

1. **M25 吞吐优化（D3-AC-11 的前置条件，无封板任务覆盖，F-15、F-54）**：PBO 异步读回或 CUDA-GL 互操作（720p 读回 13 ms、1080p 27 ms）；帧组装移出 GIL 或改为原生实现（720p 48–51 ms、1080p 75–79 ms、`therm512` 38 ms）；`encode_temp_ck` 改 zstd-1 或多线程（须同步黄金向量与 S17 的逐字节约定）；`ray_elevation` 质量位与 L2-depth 多线程压缩；效果链（畸变、雾、接触阴影、雨、2048² 投影阴影图）真实实现。完成后以 `run_s21.sh cam`（加 `--fx-proxy off`）在 A 级窗口复测，约 4.5 h。
2. **D3-AC-34 启动时长**：6 次中 1 次 6.24 s，超出部分在 `docker run` 至控制端点（4.84 s，正常 1.0–2.9 s）。建议 M24 负责人调查 dmax docker 守护进程在并发容器启停时的延迟，或改为预创建实例（`docker create` 后 `start`）；D01 冻结阈值时须明确判定统计量（逐实例最大值，或 ADR-033 的 3 次中位）。处理后以 `run_s21.sh gzcpu` 复测（约 12 min，不占 GPU）。
3. **`gz_lockstep.py` 预滚计数缺陷**（P03 工具所有者）：Env 增加 2 s 预滚后物理档推进 3620 tick，工具仍按清单 `n_ticks = 3600` 判 `step_done_25`、按 360 s 折算 `pose_history_hz`（251.39 Hz），两项误判为不通过；按实际 tick 折算为 250.000 Hz、坏步 0。应以 `n_ticks + 预滚 tick` 比较，样本率与 RTF 按实际推进时长折算。
4. **`lidar_concurrency.py judge` 随 ADR-207 更新**：C-19 确认后把同一表面距离差与"命中不一致 + 歧义"改为判定口径，`seal_ready` 才能为真。
5. **`ranked_eval` 精简缺陷仍在**（B23 遗留 1，`python/awr/bench/recorder/read.py` 缺 `lidar-v2`）：本次 9 个 Run 全部触发，D3-AC-22 的保留条款在含 LiDAR 的真实 Run 上不成立。
