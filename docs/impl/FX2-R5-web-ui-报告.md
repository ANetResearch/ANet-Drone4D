## 1 结论摘要

- **根因**（第 2 节）：D1-AC-29 的判定量"首尾各 5 min 的未强制 `JSHeapUsedSize` 中位数之比"测到的是 V8 新生代的伸缩，不是内存增长。
  1. soak 页面主线程的分配速率稳定在约 1.0–1.2 MB/s（`--trace-gc` 每分钟的 scavenge 回收量合计、60 s 分配采样 1179 KiB/s），30 min 内不随时间上升。
  2. 未强制的读数 = 保留堆 + 采样时刻的新生代占用。新生代容量由 V8 自行决定：存活量累积时扩大（复现中每次 scavenge 回收的量 3.6 → 4.4 → 6.1 → 9.8 MB，周期 1.5 → 12 s，`JSHeapTotalSize` 40 → 57 MB），分配吞吐低或发生压缩型完整 GC 时收缩（回到每次 1.5 MB、周期 1.4 s）。soak 的分配速率恰在这一门槛附近，新生代在两种量级间来回切换。
  3. 第 4 轮各 5 min 窗口中"每 5 s 上升 6 MB 以上"的大步形态所占比例为 20%、11%、33%、53%、93%、100%，中位数 34.7、34.5、34.8、36.3、38.5、43.7 MB 与之同步上升；窗口最小值 30.5–32.4 MB 几乎不动。第 3 轮比例 64%–93%，中位数 40.7–47.9 MB。验收报告所说的"后 15 min 分配速率上升"实际是同一速率下新生代变大、回收间隔变长。
  4. 保留堆没有增长：强制完整 GC 后的 `JSHeapUsedSize` 在 10 min 连续页面上为 33.05–33.9 MB，漂移 ≤ 2%；第 150 s 与第 594 s 两次堆快照按类型聚合，自身大小合计 83.34 → 83.04 MB，没有持续增长的类型。不存在保留型泄漏。
- **处置**（第 3 节，ADR-075）：度量改为**保留堆**——soak 每 30 s 经 CDP `HeapProfiler.collectGarbage` 强制完整 GC 后再读 `JSHeapUsedSize`，首尾 5 min 样本中位数之比 ≤ 20%（阈值不变、不放宽）；未强制读数的中位数之比与窗口最小值之比只作记录。按 03 §1.3 第 3 条冻结 D1-AC-29 的三个暂定阈值（保留堆增长 ≤ 20%、RSS ≤ 10%、重连 0）。
- **效果**（第 6 节）：新用例经 harness 的 6 min 自测通过（`heap_growth_pct` −0.94%）；30 min 全程运行（与注册用例相同的参数）`heap_growth_pct` +3.31%（保留堆首窗中位 30.63 MB、尾窗 31.65 MB），RSS api +0.45%、sim-core +0.003%，重连 0，GPU 池高水位不变，结束后整景帧节奏 p99 66.7 ms、> 50 ms 3.89%、最大 116.7 ms；注入 5 KiB/s（307 KB/min）的人工保留型泄漏时，新口径的保留堆斜率比无注入运行高 281 KB/min，即新口径能分辨原口径噪声（±20–30%）以下的慢速泄漏，比原口径更严。
- **未改产品代码的理由**：UI 壳与 store 只占主线程分配的约 8%（时间轴轨道刻度、读数格式化、任务与世界 store），不在 M15-NFR-014 约束的热路径上；主要分配来自引擎热路径中 double 参数的装箱（`engine/time/interpRing`、`engine/drones/DroneLayer` 与 `TrailRing`），属 web-engine，列入路线图（ADR-075 第 4 条、第 7 节）。即使把分配压到 1 MB/s 以下，原口径仍取决于 V8 的伸缩门槛，不是可靠的验收口径。

### 2.1 方法

- 第 4 轮从 t = 1037 s 到结束、以及 t = 626–686 s，每 5 s 稳定上升 6.0–6.5 MB（1.2–1.3 MB/s），每 10–30 s 回落 6–20 MB；其余时段每 5 s 只升 0.0–0.4 MB，读数之间的抖动 ≤ 1.5 MB。两种形态的切换与世界切换（k = 20、80、140）、预设（全部选中列表第一项"晴"）、Ctrl+B 都不对应，切换前后窗口最小值不变。

## 7 遗留问题与建议

1. **引擎热路径的分配（web-engine，V0.2）**：主线程约 1.2 MB/s 的分配中约 62% 来自每机每帧调用未内联函数时 double 参数的装箱（`interpRing.push` 16 个参数、`TrailRing.append`、`sampleSlot`、`slerpInto`、`buckets.radii`）。改为写入预分配的标量槽（如每个模块一个 `Float64Array` 暂存区，调用方先写槽再调用无参版本）或让调用点内联，可以把分配降到约 0.5 MB/s 量级，减少 scavenge 次数与 D1-AC-30 的 GC 停顿（第 2 轮通过、余量小）。这不影响 D1-AC-29 的新口径。
2. **UI 壳的 4 Hz 分配（web-ui，可选）**：时间轴轨道刻度绘制约 37 KiB/s（闭包 `x(t)` 与 `moveTo/lineTo` 的 double 运算在解释执行时装箱），读数格式化约 11 KiB/s，store 摘要约 25 KiB/s。合计约 8%，D1 不处理。
3. **未强制读数的历史可比性**：第 1–4 轮的 `heap_growth_pct`（19.5%、14.3%、16.5%、26.2%）与新口径不可比；第 5 轮验收报告应只引用新口径，并可在 result.json 的 extra 中查看记录项。
4. **场景装载期的保留堆**：揭开后头一分钟保留堆上升 1.5–2.5 MB，首窗含第一个页面装载期与第一次世界切换后的装载期，尾窗是装载完成后的稳态，因此首尾比值天然偏正（本机全程运行 +3.31%），阈值 20% 有足够余量；若以后要把阈值收紧到 10% 以下，宜把首窗起点放到揭开后 60 s。
