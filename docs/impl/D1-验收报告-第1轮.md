## 1 结论摘要

- 本轮测量了 D1-AC-01 至 D1-AC-35 全部 38 条（03、09、11 各分 a、b）：通过 13 条，不通过 23 条，未测 2 条（D1-AC-08、D1-AC-28，原因是工具未实现口径，且 N = 1000 的后端起不来）。
  - 含 P0 的 25 条：通过 10 条（01、11a、12、13、20、24、32、33、34、35）；另有 02、14 两条的 P0 子项全部通过，只因 P1 子项不通过而整条判不通过；
    不通过 14 条（02、03a、03b、04、06、07、09a、10、14、15、19、25、26、27）；未测 1 条（08）。
  - 只含 P1 的 13 条：通过 3 条（21、22、31）；不通过 9 条（05、09b、11b、16、17、18、23、29、30）；未测 1 条（28）。
  - D1 退出条件（G4：P0 全部通过）不满足。
- 四个根因决定了大部分不通过项：
  1. **前端 Tier S 帧节奏（web-engine，部分在 web-ui）**：深圳纯点云 p50 50 ms、p95 83 ms；整景 p50 83 ms、p95 183 ms；n200 p50 117 ms。
     同机、同标志、同钉核的 g02 研究原型 p50 33.3 ms、p95 50 ms，说明问题在产品前端。连带 03a、03b、04、05、06、09a、19、23、25、26、29、30。
     我方主线程 JS 每帧中位只有 1.6 ms，UI 壳单独贡献 p50 +16.7 ms，GC 占帧时间 5.5%（4.2）。
  2. **sim-core 运行期 numba 编译被 2 s 活性阈值杀掉，冷缓存下崩溃循环（sim，P0 阻塞）**：M09 `fleet_scan` 与 M10 `track_step` 的预热签名与运行期
     （只读 ENU 视图、float32 记分板）不一致。按交付状态 `test_s1` 50 s 内失败；本轮在补齐缓存后测得 S1 本身 9 谓词全真、×10 墙钟 159 s（4.1）。
  3. **N = 500/1000 起不来（sim，P0 阻塞）**：`AWR_SIM_N` 布设时每架机重复 51 ms 的平坦点搜索，N = 1000 约 51 s，超过 15 s 启动宽限（4.4）；
     ladder n1000 剧本在一个 tick 里加 1000 架（O(N²)），超过 2 s 活性阈值（4.3）。D1-AC-07、09b、27 因此无法在生产配置下测量。
  4. **测量工具缺口**：`bench_state --clients 3 --with-flight60` 与 `fleet_ladder --with-recorder/--clients` 只解析参数不执行；latency 用例缺命令到可见、
     关注集切换、×10 HOLD 三项；harness 原先会抢占操作员席位、看不到后端重启、读不到服务端窗口指标。本轮已在工具层修复后者（第 6 节）。
- 其余不通过项：S2、S4 最小间距约 5.7 m、S5 电量 0.239（17）；S3 ×1 与 ×10 accepted 时刻差 8.5 s（16）；挂死检出 3.34 s 与毒性 checkpoint 未回退（11b）；
  seek 最大 1.4–2.4 s 与 20× HOLD 2.5%（18）；事件补齐有 2–3 个丢弃未补（10）；预设切换期间 > 100 ms 帧 65%（19）；Tier A 功能矩阵未实现（14）；
  soak 中后端 RSS 端点增长 70–91%（29）。
- 通过项：六城世界校验与单城构建（26.9–31.5 s）、契约与 golden、动力学对拍、chaos-core、设计体系与可用性、画布尺寸稳定、交互、远程访问、
  walking skeleton、早期数据源、确定性重仿真、Mock 重建链路。
- 暂定阈值：整景、n200、时延的暂定阈值不建议按本轮数据冻结或放宽（数据反映缺陷，不是可达上限）；填充率 95% 与 Worker 解码 2 ms 可冻结；
  冷启动 4.0 s 视前端修复后的复测决定（第 5 节）。

### 2.3 运行协议执行（ADR-033、18 §3）

- PR-1 排他锁：全部性能用例经 harness 以 `flock -x runs/.perf.lock` 执行；世界构建计时、g02 对照、numba 预热、冷缓存 S1 证据也都在同一把排他锁下运行。
- PR-2 开跑前 load ≤ 4：harness 在每次运行前轮询 1 分钟 loadavg（10 s 一次，最长 10 min）；本轮没有出现 PERF-E002。
- PR-3 三次取中位：除注册表声明 `runs: 1` 的功能型用例外均为 3 次；每次新浏览器进程、新临时 profile、新后端（新 run id）。
- PR-4/PR-5 运行内负载：harness 每 5 s 采样，记录在各用例 `result.json` 的 `runs[].load{pre,max,mean}`。帧节奏类用例运行内最大值为 4.2–10.6（soak 10.6、ui-overhead 8.7、layers 8.8–9.2，其余 ≤ 7.9），均 ≤ 12.8，帧节奏阈值全部强制执行。画质、点数与 CPU 类阈值按运行内均值 < 6 判定：quality 为 5.2–5.7（判定）；soak 均值 9.4、layers 7.1–7.6，这两个用例里没有 CPU 与画质类门禁项。
- PR-6 钉核：后端使用 `perf` profile（api core0、sim-core core1），Playwright 与 Chromium 在 `taskset -c 2-6`；harness 的亲和性检查没有报 PERF-E014。
- PR-7 构建形态：见 2.2；harness 快照校验没有报 PERF-E015。
- PR-8 数据前置：`make validate` 六城 0 错误 0 警告，`make flight60-check` 通过。
- PR-11 异常补跑：pageerror、GL 错误与（本轮补上的）后端进程重启都触发一次补跑。
- 错误码：全部结果中没有 PERF-E002、E005、E007、E014、E015；PERF-E008 出现在 storm.rtl、ladder.front.n1000（后端起不来）；PERF-E011 只表示门禁指标无值（后端起不来或用例不产出该值）；PERF-E013（离散度告警）只出现在四个用例的 TTFP 上（扣除预热后只有几毫秒，相对离散度大）。

## 4 关键发现与诊断（按修复区域）

区域取值与结构化结果一致：sim（sim-core、supervisor 与剧本运行时）、gateway（api、网关、回放与 IPC 工具）、web-engine（点云、渲染、探针）、web-ui（UI 壳与面板）、world（世界与重建数据）、other（测量工具与跨模块）。

### 4.1 sim：运行期 numba 编译与 2 s 活性阈值导致崩溃循环（P0 阻塞；冷缓存下影响 D1-AC-15 与全部带机群的用例）

- 现象（首轮 `flight60.shenzhen.full`，证据 `runs/acceptance/round1/diag/flight60.shenzhen.full.invalid-coldcache/`）：
  - 每次运行的 60 s 内 sim-core 被 supervisor 杀掉并重启 5 次（`proc hung`，`heartbeat_age_ms` 约 2030），第 6 次熔断进入 FAILED；
    页面 `net.swarmHz = 0`、`epoch = 65535`，整景实际上没有无人机数据。
  - faulthandler 栈指向 `awr/sim/safety/fleet_guard.py:92` → numba `_compile_for_args`：主循环里在为 `fleet_scan` 编译新签名。
- 根因（已核实）：
  - `awr/sim/safety/kernels.py::warmup()` 只用可写的 float64/int64 数组调用 `fleet_scan`；运行期 `fleet_guard` 传入的是 M08 的
    只读 ENU 视图（`Array(float64, 2, 'C', readonly)`）与 float32/int32 记分板。numba 按签名缓存，于是运行期第一次出现两架以上机体时
    在主循环内 JIT 编译（单核约 3–4 s）。
  - supervisor 的 sim-core 活性判据为 StateRing 心跳 `stale_s: 2.0`（`configs/runtime.yaml`），编译未完成就 SIGKILL，编译结果永远写不进缓存，
    形成崩溃循环。缓存索引显示：`kernels.fleet_scan-190`（当前源码行号）只有预热签名；源码修改前的 `-189` 版本曾有两种签名。
  - M10 `awr/sim/planning/kernels_track.py::warmup()` 有同样的问题：预热用可写 `p_enu`，运行期 `tracker.stage` 传入只读 `S.enu.pos`；
    缓存缺该签名时，S1 起飞后约 18 s 处 sim-core 被杀一次（证据 `diag/flight60.shenzhen.full.invalid-trackerjit*/`）。
  - `make run` 的预热目标（`numba-warm`、`m10-numba-warm`）也只覆盖预热签名。
- 冷缓存下的 D1-AC-15 证据：`pytest tests/e2e/test_scenarios.py::test_s1`（ci profile）50 s 内失败：sim-core 连续 6 次 `hung` 后熔断，
  `core proc failed in ci profile`（`diag/test_s1-cold.log`）。即从当前代码的干净缓存出发，S1 无法运行。
- 本轮的处理（环境步骤，不改被测代码）：
  1. `.cache/acc1/prime_numba.py`：以运行期类型调用一次 `fleet_scan`，把只读与 float32 签名写入 `NUMBA_CACHE_DIR`（`diag/prime_numba.log`）。
  2. `.cache/acc1/prime_runtime2.py`：用一份把 sim-core `stale_s` 放宽到 120 s 的 runtime 配置副本（`.cache/acc1/runtime-prime.yaml`），
     依次运行 S1（perf、ci）、ladder n200、n1000、soak、free 剧本，让其余运行期签名编译完成并入缓存（`NUMBA_DEBUG_CACHE=1` 日志确认
     `kernels_track.track_step-119` 写入）。
  3. 之后的全部性能用例在缓存命中的状态下测量；harness 新增的 PERF-E008 检查确认这些运行中 api、sim-core 没有重启。
- 修复建议（区域 sim，M08、M09、M10）：
  - 各模块 `warmup()` 按运行期真实 dtype 与只读标志预热（M09 `fleet_scan`：只读 pos/vel、float32/int32 记分板；M10 `track_step`：只读
    `p_enu`），并为每个 njit 核加一条"预热签名覆盖运行期签名"的单元测试（构造运行期参数，断言 `len(fn.signatures)` 不增加）；
  - `make run` 的预热目标改为调用各插件的同一预热入口；

### 4.3 sim：ladder n1000 剧本在一个 tick 内加 1000 架，超过 2 s 活性阈值（P0，D1-AC-27 RTL 阻塞，D1-AC-09b 连带）

- 现象：`storm.rtl`（`ladder-shenzhen` profile n1000）3 次运行（含 PR-11 补跑共 6 次）都在后端阶段失败：`mark ladder.steady not seen
  within 150 s`；每次 sim-core 日志 6 次 `child started` 后熔断。faulthandler 栈都停在剧本导演的 `add` 阶段：
  `mission/director.py:186 _step_setup → core/command.py submit_internal/_fleet_op → runtime/main.py admit_add/add_vehicle`，
  采样点分别落在 `core/roster.py:79 free_slot`、`fleet/state.py:123 refresh`（ENU 视图刷新）与 `runtime/main.py:484`
  （每加一架都全量重建 `agent_slot`）。
- 根因：导演在同一个 tick 里对 1000 架逐个提交 `fleet/add`，每次添加都有 O(N) 的工作（空槽线性查找、ENU 视图刷新、`agent_slot`
  全量重建），整体 O(N²)，单核上这个 tick 超过 2 s，StateRing 心跳过期，supervisor 判 `hung` 并 SIGKILL，剧本从头再来，6 次后熔断。
  用放宽到 120 s 的配置副本运行同一剧本时能正常进入稳态（`diag/prime/`）。
- 影响：生产配置下所有用 ladder n1000 的用例都无法开始：`storm.rtl`（D1-AC-27 P0）、`ladder.front.n1000`（D1-AC-09b）、
  `storm.linkdrop`、`gw-10clients`。
- 建议（区域 sim，M10 导演 + M08 roster 与 FleetState）：`add` 阶段按每 tick 上限分批提交（例如 32 架）；`add_vehicle` 增量维护
  `agent_slot`，`free_slot` 用空闲表，ENU 视图在一个 tick 末尾统一刷新；加一条"n1000 剧本 setup 期间单 tick 墙钟 < 1 s"的用例。
- 诊断运行（`AWR_PERF_RUNTIME_CONFIG` 指向放宽活性阈值的配置副本，1 次，不判定，`diag-relaxed/`）：
  - `storm.rtl`：全机 RTL 下发后，我方 > 50 ms 长帧 57 次，Toast 2 条，DroneRail 实际渲染行比可见行多 989 行（虚拟列表没有生效，web-ui），
    sim-core 单步 p99 77 ms、最大 94 ms，tick 数据年龄 p99 22.8 ms（sim）。
  - `ladder.front.n1000`：p95 550 ms、> 100 ms 66.0%，Worker 解码 p95 0.285 ms；sim-core CPU 0.80 核、单步 p99 72 ms（剧本驱动的 1000 架，sim）。

### 4.4 sim：`AWR_SIM_N` 布设时每架机重复搜索平坦出生点，N ≥ 500 时 sim-core 超过启动宽限（P0，D1-AC-07 阻塞，D1-AC-08、28 连带）

- 影响：D1-AC-07 的门禁规模 N = 1000 无法测量；`fleet-ladder.concurrent`（D1-AC-28）同样起不来；若 D1-AC-08 的工具补齐，也会卡在这里。
- 建议（区域 sim，M08）：`_flat_spot()` 只算一次（或缓存到 `cfg.spawn_xy`）；修复后复跑 `fleet-ladder`。按本轮 N = 200 的数据（单步 p99 中位约
  3.4 ms、最大 12–15 ms，CPU 0.37 核），N = 1000 达到 p99 ≤ 3 ms、最大 ≤ 12 ms 仍有风险，需要一并处理 4.6 列出的固定开销。

  最大 17.5 ms，追帧饱和 0；p99 与最大值仍超门槛。注意负载脚本只发出 4 条命令（4.7），机体基本停在地面，真实飞行负载下的数值会更高。
- 工具侧：`fleet_ladder/run.py` 在 sim-core 起不来时不报错，写出含 `NaN` 的非法 JSON；本轮在 harness 侧把 NaN 读成 null（第 6 节），
  工具本身应改为该规模点失败并以非零退出码结束（M08）。
