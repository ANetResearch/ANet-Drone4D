# D2.2-R-world 对抗式复核报告

> 任务：D2.2-R-world 世界隔离修复与六城模拟监测展示的对抗式复核（只测量与举证，不修复）｜ 完成时间：2026-10-13 18:10 UTC（西雅图 11:10）｜ 本地服务端口偏移 800
>
> 目标：验证用户原话反映的缺陷——“切换城市的时候，最开始在 synthcity 中布置的目标物、视野、感知范围等都被带到不同的其他的地图里面去了”——是否已被修复，以及“在其他的地图中也加入模拟的无人机监测任务和对应的目标物”是否已经落实。只报告有证据的问题，不修改代码。

## 0. 结论

1. **用户报告的核心缺陷（synthcity 的实体串到其他城市）已经修复**，且修复比用户原话描述的范围更广：不只是 synthcity 与六城之间，六座 UrbanScene3D 城市彼此之间（直接切换、不经过 synthcity）、浏览器前进 / 后退、整页刷新、带 `sel` 深链接直达、快速连续切换（350 ms 间隔连切 8 次）等全部路径下，均未观察到异城实体残留或串入。这部分已由本次复核的七个独立测试场景（见第 2 节）与官方新增的 `perf/d22/world-isolation-live.spec.ts`（本次以端口偏移 800 重新运行，3 个用例全部通过）共同印证。
2. **六城“模拟无人机监测任务与目标物”已经接入**（`tools/sim/gen_city_watch.py` 生成剧本 + `tools/sim/capture_city_watch.py` 离线录制 `worlds/<city>/show/show.awrrt`，前端以 `fake:` 回放源播放，`lib/demo.ts` `CITY_SHOW_FIXTURE`），六城均能看到各自的机队、目标物与任务，与 synthcity 互不干扰。
3. **但本次复核发现一个未修复、复现稳定的功能缺陷（建议列为阻塞项）**：六城中 **shenzhen、newyork 两城的“接力监控”（relay_watch）任务在录制展示里从一开始就判定为“不可行”（INFEASIBLE）、机群 0 架、覆盖 0%，并在之后至少一分钟内保持该状态不恢复**。也就是说，这两座城市对外展示的“两个监测任务”实际只有一个在真正运行，另一个从未运行过，与用户要求的“加入模拟的无人机监测任务”不完全相符（见第 3 节，附根因与证据）。
4. 另有两项标注一致性方面的次要问题：手机横屏 / 竖屏布局下，“共享展示”与“模拟回放·只读”两种状态只用图标区分、没有文字，用户在手机上无法单凭界面文字分辨正在看的是实时仿真还是离线录制回放；平板顶栏面包屑仍写死显示“共享展示”，与同屏右侧角色徽标的“模拟回放·只读”不一致（见第 4 节）。
5. 其余检查项（GPU 规范最小上限下的渲染错误、识别物与机体是否悬空 / 嵌入建筑、各城环境与昼夜差异）未发现异常，细节见第 5 节；第 6 节说明本次复核方法与局限。

### 3.2 根因分析（代码阅读，未改代码，供修复方参考）

1. `python/awr/sim/tasking/book.py`、`runtime.py:879` 把 `INFEASIBLE` 列为任务的**终态**之一（与 `DONE`、`CANCELED`、`FAILED` 同级），一旦进入不会自行恢复——这与第 3.1 节“36 秒内持续不可行”的观察一致。
2. `gen_city_watch.py` 生成每城剧本后，用 `engine_feasible()`（`tools/sim/_engine_check.py`）跑一遍真实引擎做最后把关。但 `_engine_check.py` 的判定逻辑是：**只要全部任务的状态离开 `PLANNING`（通常几十到几百毫秒）就立即退出循环**并在那一刻读一次状态；`--seconds` 参数（`gen_city_watch.py` 中固定传 `4`）只是整个等待的上限，并不代表会持续观察 4 秒。也就是说，这道把关只能挡住“任务一开局就不可行”的剧本，**挡不住“任务先进入正常状态、几秒钟后才因中继站位搜索失败而转为不可行”的剧本**——而 `relay_watch` 恰恰是一个持续重新评估接力站位的任务类型（`python/awr/sim/tasking/relay.py` 的 `request_station`/`_on_station` 在“initial”“wake”“reacquire”等多种时机反复发起站位搜索作业）。
3. `capture_city_watch.py` 用真实引擎跑满 120 秒（默认 `--seconds 120`）把这段过程**原样录制**进 `.awrrt`，前端又把它当循环播放源（`loop=1`），于是“几秒后 relay_watch 失败”这个一次性的引擎行为被永久固化进了对外展示的录制内容，每次循环都会重演一次、此后再也不会恢复——这正是公开站上每一个访客打开 shenzhen 或 newyork 后几秒内都会看到的现象。
4. 任务详情页“尚未分解出工作项”与 `relay.py` 的 `raise_infeasible()` 在 `request_station` 的 `reason="initial"` 阶段即可触发一致：说明失败发生在任务刚开始的第一次站位搜索，尚未分配到任何工作项，而不是运行一段时间后才failed。

### 3.3 影响与建议

- 影响：按公开站当前这份工作区的状态直接发布，shenzhen、newyork 两城对外展示的“两个模拟监测任务”里有一个（接力监控）自始至终不会运行，与用户“在其他地图中加入模拟的无人机监测任务”的要求不完全相符，且界面会持续显示一条红色“不可行”的任务行和一次性的告警提示，观感上也不像是预期中的正常演示状态。
- 建议（供负责该功能的工作包参考，本任务不执行修复）：
  1. 让生成 / 录制流程能够发现“任务在 4 秒把关之后才变得不可行”的情况，例如把 `capture_city_watch.py` 录制结束后扫一遍事件流里的 `task.*` 终态（报告与 W1 报告 §7.2 已经提到可以用 `task.*` 与 `target.discovered` 事件核对任务是否真的在跑，但看起来 W2 的录制流程并未对 `INFEASIBLE` / `FAILED` 做事后校验),若发现任务提前终态化则判为本次生成失败、换一组种子重试（`gen_city_watch.py` 已有 `GeoRetry` 重试机制，可以复用同一条路径）。
  2. 或者在 `tools/sim/_engine_check.py` 里把等待时间从“任务一离开 PLANNING 就退出”改为真正等满一段更长的墙钟时间（尤其是含 `relay_watch` 的剧本），更贴近实际录制时长。
  3. shenzhen、newyork 两城需要用新的种子重新生成剧本并重新录制 `show.awrrt`。

## 4. 次要发现：界面标注“模拟 / 回放”的一致性

### 4.1 手机布局没有文字区分“共享展示”与“模拟回放”

`apps/web/src/ui/mobile/parts.tsx` 的 `RoleChip` 组件在 `compact` 模式下（`apps/web/src/ui/mobile/MobileShell.tsx:76` 的 `<RoleChip compact />`，手机顶栏唯一调用处）把文字标签整段省略（第 109 行 `{compact ? null : t(key)}`），只保留一个图标：实时共享展示用 `layer.visible`（眼睛图标），城市录制回放用 `tl.history`（历史 / 时钟图标）。手机端“更多”菜单（`MoreMenu`，同文件第 116 行起）也没有提供这一区分的文字入口。也就是说，**手机用户仅凭界面文字无法判断当前看到的是 synthcity 的实时仿真还是某座城市的离线循环录制**，只能通过辨认一个小图标的形状。桌面（`AppHeader.tsx`）与平板角色徽标（`TabletShell.tsx` 引用的同一 `RoleChip`，非 compact 模式）均有完整文字“模拟回放·只读”，不受影响。

证据：`.cache/impl/shots/d22r/d22r-mobile-synthcity.png`（顶栏图标为眼睛）对比 `d22r-mobile-suzhou.png`（顶栏图标为时钟，均无文字）；代码位置 `apps/web/src/ui/mobile/parts.tsx:104-112`、`apps/web/src/ui/mobile/MobileShell.tsx:76`。

### 4.2 平板顶栏面包屑与同屏角色徽标文案不一致

`apps/web/src/ui/mobile/TabletShell.tsx` 第 71 行的面包屑（`data-crumb="world"`）在非 `static`、非沙盒时一律显示 `t('mobile.shared')`（“共享展示”），没有像同一文件引入的 `RoleChip`（第 75 行）那样区分 `isCityReplay`；也就是说平板上同一屏会同时出现“shenzhen › 共享展示”（面包屑）与“模拟回放·只读”（右侧徽标）两种措辞，内容不矛盾但不统一。未在本机实际截图验证（代码读证据已足够明确且改法清晰），建议与第 4.1 一并由负责该组件的工作包处理。
