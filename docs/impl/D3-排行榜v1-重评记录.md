## 1 评测器修正（0.3.0）

### 1.1 搜索赛道的计分事件

- **缺陷**：评测器 0.2.0 的计分事件只取 plan.json 的 `annotations[]`（`agentsdk.task.scored_events`），而 `target_search` 事件没有注释。它的计分类型 `target_window` 由门 3 验证器写在事件真值 `key_events[]` 中，因此计分事件集为空，EC、EU、AO、CE 恒为 0（B21 §0.2 第 1 条）。
- **计分事件集**（`awr.bench.eval.truth.scored_event_set`）：在注释之外，加入事件真值 `key_events[]` 中满足以下两个条件的类型化关键事件：
  - 类型属于任务契约 `scored_event_types`；
  - 该类型没有同类型注释。

  目标搜索即每个 60 s 窗口一个 `target_window_k`。关键事件的不完整区域取其所属 `target_present` 的 `in_incomplete_region`，区间取 `interval_ms`；它们以合成真值行接入 `ec.exclusions` 与 `ao.truth_intervals`。
- **其他事件类型不变**：注释类型的赛道（reid、handoff、vehicle），任务契约的计分类型只来自注释，关键事件不进入计分集。测试 `test_annotation_events_unchanged_by_key_events` 在真值中加入同类型与非计分类型的关键事件，评测结果仍逐字节一致。dmax 上 600 次非 search 运行的重评也逐字节一致（§3）。
- **EU 的目标搜索口径**（`eu_target_set`，AWR-05 §5.2.8 规则 5、M23 §15.3 规则 4、M27-FR-176）：
  - EU 真值为事件真值 `events[]` 中的 `target_present`，`found` 经 `report_map` 映射到它；
  - report 须证据关联到目标，且定位误差 ≤ 5 m；
  - 定位误差取水平距离，目标位置取 report 窗口末时刻（截断到在场区间）的磁带位置；
  - 新阈值 `Thresholds.eu_found_m = 5.0`，取自 §5.2.8 的 target_search 行。

  其他事件类型的 EU 事件集与类型映射不变。
- **`inputs.event_truth_sha256`**：只有注释计分时与 0.2.0 相同；有关键事件进入计分集时，为 `{annotations, key_events}` 的规范 JSON 摘要。

### 1.2 隐藏真值经 HiddenStore 读取

`awr.bench.eval.truth.TruthAccess` 是评测器读取真值的唯一入口：

- 缺省直接读文件，用于 dev 事件与刚写完的运行目录；
- `TruthAccess.hidden(hs, event_id, run_id, job)` 以 Evaluator 服务主体经 `HiddenStore` 读取：每个真值文件（`event_truth.json` 与运行真值）一条 `truth_read`（op `read`）；打开事件版本目录（磁带、plan.json、锚点）前一条授权审计（op `evaluate`）；非评测员主体返回 691。

`evaluate_run` 与 `load_run` 新增两个参数：

- `truth_dir`：已移入隐藏区的运行真值目录 `hidden/<eid>/truth/runs/<run_id>/`；
- `access`：真值读取入口。

测试 `test_hidden_truth_read_through_hidden_store` 核对三点：经隐藏区读取的结果与直接读取逐字节一致；审计覆盖的文件集合正确；研究员主体返回 691。

### 1.3 `truth_sha256` 口径（B33 遗留 3）

在 B33 给出的两个方案中，选择收窄评测器的 `truth_sha256` 口径并递增评测器版本，不改 `retention.TRUTH_MIN_FILES`（retention 归 K17）：

- 评测器只读运行真值 `RUN_TRUTH_FILES = (contacts.jsonl, fleet.npz, l1.jsonl, l2.jsonl)`，均在 `retention.TRUTH_MIN_FILES` 之内；
- `inputs.truth_sha256` 只覆盖这几个文件中存在者：按文件名排序，逐个 `名称 ‖ 0x00 ‖ 内容`；
- `truth/run_<id>.mcap` 与 `run_seed.json` 不进入摘要。

因此排名运行精简后，由保留文件复评逐字节一致（`test_truth_digest_survives_ranked_compaction`）。dmax 上 800 次运行的 `truth_sha256` 全部随口径改变，属预期；`raw_mcap_sha256` 与 `tape_sha256` 全部不变。

## 5 L2 首拍动作超时：原因判定与重跑（未执行）

### 5.1 判定：平台原因

B21 中 static_guard 在 crop-handoff-102 上有 3 次 L2 运行四项为 0：`v1-l2-static_guard-crop-handoff-102-k3r1`、`-k4r0`、`-k4r1`。

- **同一时刻启动**：三次运行在 2026-10-21T23:19:12Z、23:19:14Z、23:20:08Z 启动，即 L2 基线进程池的 3 路在 56 s 内同时开始。同时还有两个 L2 提交在评测，宿主负载为 15 至 120。
- **9 个 Agent 全部在首拍超时**：三次运行共 9 个 Agent 容器（std3-l2 分轨，每次运行 3 机，p600_bench），都只在 k = 0 超时一次（661，`step_budget_s = 2.0`），之后 2399 拍全部按时。
- **超时导致零分**：首拍动作被丢弃，static_guard 的起飞指令只在首拍发出，因此全程未起飞，四项为 0。
- **全量扫描**：扫描全部 400 次 L2 运行，"同一 Run 内 3 个 Agent 在同一拍超时"共出现在 20 次运行中，拍号各不相同。其中首拍（k = 0）有 4 次：上述 3 次，以及提交 close_track 的 `sub-5umzyjgoaknw5eou-crop-search-102-k0r1`。后者的 uav-01 此后每拍超时、未产生观测，在 v1.1 中四项为 0，使 close_track 的 L2 search EC 为 0.950。L1 无超时。
- **结论**：独立容器中的三个 Agent 同拍超时，只能来自共同的宿主停顿，与策略无关。按 B21 遗留 4 的口径（"全体 Agent 同拍首拍超时"判为平台原因），这 3 次运行属平台原因，应按 D3-AC-57 (d) 重跑并替换。

### 5.2 重跑工具（已实现，未在 dmax 执行）

`board_v1_formal.py rerun-platform` 的处理步骤：

1. 原运行目录与隐藏区运行真值改名为 `<run_id>.superseded-<n>`，保留不删；
2. 以 EvalStore 中的同一种子重新运行与评测；
3. 新运行的真值移入隐藏区；
4. 原评测行移到 `rows.superseded.jsonl`（带原因），追加新行；
5. 发布两次核对逐字节一致。
